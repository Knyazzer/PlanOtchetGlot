# Дебаг-кейс 2026-08-10 — «отпуск-сирота» в дне сотрудника

> Разбор бага: как искали, в чём была причина, как решили. Родитель: [CLAUDE.md](../CLAUDE.md).
> Смежное: правило [[data-immutability-audit-nexus]], хрупкость «единый статус vs dayFormat» (BACKLOG).

## Симптом

В кабинете тестового пользователя на 14 и 20 августа висел **«Отпуск»**, хотя:
- ручного тумблера отпуска в UI нет (отпуск только через заявление → согласование);
- заявку **отозвали с аккаунта руководителя**, а день всё равно показывал отпуск.

Первая гипотеза Влада: **паразитная зависимость от нового drag** — «появился, когда таскал задачу на это число».

## Как отлаживали (методология — важнее самого бага)

1. **Отделили корреляцию от причины — по фактам БД, не по ощущениям.** Посмотрели `nexus.day_entries` за 14/20:
   - тип дня — `day_format = 'vacation'`;
   - **`created_at == updated_at`** = 8–9 августа, т.е. записи созданы **до** того, как drag-механика вообще появилась (10 августа). → drag ни при чём (иначе `updated_at` был бы сегодняшним).
2. **Проверили код-путь drag.** `onDropOnDay → moveMut → PATCH /tasks/:id` правит **только `Task`** (`startDate`/`deadline`), в `day_entries` не пишет. Подтвердило: зависимости нет.
3. **Пошли по настоящему источнику `vacation` — заявки.** `nexus.requests` тестового:
   - Заявка 05–20 → `canceled`; Заявка 08–14 → `revoked` (сегодня 07:42).
4. **Сверили инварианты.** Гард `cancel` требует `status='pending'` → отменённая заявка **никогда не отражалась** в дне (значит 20-е — сирота, «владельца» нет). Для отзыва проверили, что `unreflectLeave` **должен** был удалить день: `date` в БД **точно совпадает** (`date = DATE '2026-08-14'` → true) с условием `deleteMany`. Значит WHERE верный → на отзыве `unreflect` **просто не выполнился**.

## Причина

Оба дня — **осиротевшие `day_entries` с `day_format='vacation'`**, за которыми нет активной одобренной заявки. Механика опирается на `unreflectLeave` (удалить отпускной день при отзыве), но он по этим дням не отработал. Наиболее вероятно:
- **отзыв в 07:42 попал в залипший `tsx watch` dev-API** (Windows — повторяющаяся боль, память `nexus-dev-api-tsx-watch-stale`): статус заявки обновился, а откат дня в старом инстансе не выполнился;
- усугубляет **архитектурная хрупкость**: день хранит **копию** статуса, а не выводится из активных заявок → сбой одного звена оставляет сироту, которую из UI не убрать.

## Решение

1. **Данные (dev):** удалили две ложные записи — ровно то, что должен был `unreflect`:
   `DELETE FROM nexus.day_entries WHERE user_id=… AND date IN ('2026-08-14','2026-08-20') AND day_format='vacation';` → день вернулся к графику.
2. **Харденинг (в BACKLOG):** выводить `day_format` из активных заявок **или** идемпотентная сверка/чистка сирот; **завести аудит-лог смены `day_format`** (сейчас истории смены статуса дня нет — поэтому «какая функция записала» из журнала не показать).

## Уроки / чек-лист на будущее (как ловить такие баги)

- **Сначала БД + `created_at`/`updated_at`, потом выводы.** Таймстампы мгновенно отделяют «до фичи / после фичи» и убивают ложную гипотезу (здесь — «виноват drag»).
- **Корреляция ≠ причина.** «Появилось, когда я делал X» — проверять код-путь X: пишет ли он в затронутую таблицу вообще.
- **Идти от данных к владельцу.** `vacation` в дне → кто ставит (`reflectLeave`) → есть ли активная заявка → сверить статусы/гарды/диапазоны.
- **Проверять инвариант удаления точечно** (совпадение ключей `date`/`format`), чтобы отличить «WHERE не тот» от «код не выполнился».
- **Нет аудит-лога — заводи.** Отсутствие истории смены `day_format` затянуло разбор; для состояний, меняемых из нескольких путей, аудит обязателен.
- **Windows `tsx watch` залипает** — при «действие прошло, а эффекта нет» первым делом подозревать устаревший dev-инстанс (curl живой API / перезапуск).
