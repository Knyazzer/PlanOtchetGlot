# Стратегические цели (квартал/год) — спека механики

> Черновик от оси агентов, 2026-07-22. Источник — голосовой бриф Влада (ежеквартальные
> стратегические встречи: что поставлено → что сделано / не сделано и почему → что ставим).
> Статус: **ждёт ревью Влада**. Три решения приняты по умолчанию и помечены `[дефолт]` —
> их можно поменять до начала реализации.

## 0. Подтверждённые решения (Влад, 2026-08-08)

- **Отдельная вкладка «Стратегия»** (стратегия компании). Позже будет много стратегий (HR и др. направления) — но пока только этот функционал, без доп.вещей.
- **Видимость — только свой департамент** (не «все»; межведомственную видимость закрываем).
- **Прогресс/закрытие — ВРУЧНУЮ**: цель закрывает сам ответственный (он решает когда — хоть 2 задачи, хоть 10 000). Никакого автопроцента. При закрытии — статус + обязательный «итог/почему».
- **К цели привязываются задачи И/ИЛИ трек** (оба, не выбор): `Task.goalId` — человек пишет себе задачи и цепляет к цели; `Track.goalId` — создаёт трек, вешает на цель, подключает людей, они ведут задачи в треке; результат людей = в рамках цели. Это отвечает на открытый вопрос из [[nexus-tracks-goals-model]] — оставляем ОБА `Task.goalId` и `Track.goalId`.

## 1. Суть механики

В компании проходят регулярные (ежеквартальные) стратегические встречи. На них:
ставятся задачи на квартал/год, идёт отчёт по прошлым задачам (сделано / не сделано /
почему), формируется список на следующий период.

Nexus получает первоклассную сущность **стратегическая цель** с каскадом:

```
Директор департамента  →  цели ДЕПАРТАМЕНТА на период
Руководитель отдела    →  цели ОТДЕЛА, опционально прикреплённые к цели департамента
Сотрудник              →  видит цели своего департамента и отдела в ЛК,
                          отмечает вклад из план-отчёта дня
```

Детализация «руководитель назначает исполнителей на конкретную цель» — **не делаем**
(решение Влада из брифа): достаточно видимости на уровне департамента/отдела.

|---|--------|--------------------|--------------|
| 1 | Прогресс цели | Статус (`active/done/partial/dropped`) + обязательное поле «итог/почему» при закрытии периода | вехи-чекпункты с автопроцентом; ручной % |
| 2 | Вклад сотрудника | Отметка из план-отчёта дня: строка «что сделал» + ссылка на цель; все отметки собираются в хронику цели | привязка оперативных Task к цели (фаза 3) |

## 3. Модель данных (Prisma, схема `nexus`)

```prisma
model StrategicGoal {
  id           String    @id @default(uuid())
  title        String
  description  String?
  // уровень каскада: цель департамента ИЛИ цель отдела
  deptId       String                    // всегда: департамент-владелец
  divisionId   String?                   // null = цель уровня департамента
  parentGoalId String?                   // цель отдела → цель департамента (опционально)
  horizon      String                    // 'quarter' | 'year'
  periodKey    String                    // '2026-Q3' | '2026'
  status       String    @default("active") // active | done | partial | dropped
  outcome      String?                   // «итог/почему» — ОБЯЗАТЕЛЕН при закрытии не-active
  carriedFromId String?                  // перенос из прошлого периода (цепочка переносов)
  sortOrder    Int       @default(0)
  createdById  String
  createdAt    DateTime  @default(now())
  closedAt     DateTime?                 // момент фиксации итога
  closedById   String?
}

model GoalContribution {
  id        String   @id @default(uuid())
  goalId    String
  userId    String
  date      DateTime @db.Date            // день, к которому относится вклад
  text      String                       // «что сделал по этой цели»
  createdAt DateTime @default(now())
  // divisionId-снапшот НЕ нужен: цель сама принадлежит деп/отделу
}
```

Заготовка (в схему сразу, эндпоинты — фаза 3, по образцу «заготовок в чатах»):
`Task.goalId String?` — привязка оперативной задачи к стратегической цели.

### Инвариант неизменяемости (железное правило Nexus)

- Закрытый период (`closedAt != null` у цели / прошлый `periodKey`) — **read-only**:
  цели не редактируются и не удаляются, вклады задним числом в закрытый период не добавляются.
- `deptId`/`divisionId` цели — снапшот на момент создания: реорганизация структуры
  не переписывает прошлые кварталы (тот же приём, что `DayEntry.divisionId`).
- Незакрытые цели прошлого периода не «висят» — их судьбу фиксирует закрытие периода
  (см. §6): done / partial / dropped / перенос.

## 4. RBAC (существующие уровни member < head < director)

| Действие | Кто может |
|----------|-----------|
| Создать/править/сортировать цель **департамента** | director этого департамента, admin |
| Создать/править цель **отдела** (+прикрепить к цели департамента) | head этого отдела, director департамента, admin |
| Закрыть период (статусы+итоги) по департаменту | director, admin |
| Читать цели департамента и его отделов | все члены департамента (member+) |
| Добавить вклад | любой член департамента — к цели своего департамента или своего отдела |

Модульный грант (реестр `/access`): ключ `org.strategic`, `editLevel` по таблице выше —
чтение остаётся у всех членов департамента независимо от гранта.

## 5. API-контракт (`/strategic-goals`, файл `routes/strategic-goals.ts`)

```
GET    /strategic-goals?periodKey=2026-Q3[&deptId=…]   — цели периода в охвате пользователя
                                                          (его департаменты; admin — все)
POST   /strategic-goals                                 — создать (Zod; RBAC по уровню)
PATCH  /strategic-goals/:id                             — title/description/parentGoalId/sortOrder
                                                          (только в открытом периоде)
DELETE /strategic-goals/:id                             — только в открытом периоде, только автор-уровень
GET    /strategic-goals/:id/contributions               — хроника вкладов (+имена)
POST   /strategic-goals/:id/contributions               — { date, text } (только открытый период)
POST   /strategic-goals/close-period                    — { periodKey, deptId,
                                                            results: [{goalId, status, outcome,
                                                                       carryOver?: bool}] }
                                                          — атомарно: статусы+итоги+closedAt,
                                                          carryOver создаёт копии в следующем
                                                          периоде с carriedFromId
```

Чеклист нового роута обязателен: регистрация в `server.ts`, префикс в `apps/web/nginx.conf`,
`preHandler` auth, Zod `.safeParse`, тест рядом, обновить таблицу API в CLAUDE.md.

`periodKey` вычисляется на сервере из даты по правилу: кварталы `YYYY-Qn`, год `YYYY`.
Текущий период — derived, никакого «активного флага» в БД.

## 6. UI

1. **Страница «Стратегия»** (пункт навигации или вкладка в Tasks рядом с «Треки»):
   - селектор периода (текущий квартал по умолчанию; прошлые — read-only с плашкой «период закрыт»);
   - дерево: департамент → его цели → цели отделов (прикреплённые — под родительской целью,
     непривязанные — отдельным блоком отдела);
   - у каждой цели: статус, счётчик вкладов, горизонт (квартал/год), маркер переноса
     («переносится 2-й период» — по цепочке `carriedFromId`);
   - прогресс-полоса периода: «до конца квартала N дней» (по производственному календарю
     уже есть `services/calendarRf.ts`).
2. **Виджет в ЛК/на Главной**: «Цели квартала» — цели моего департамента и моего отдела,
   дни до конца периода, кнопка перехода в Стратегию.
3. **План-отчёт дня (DayModal)**: блок «Вклад в цели» — выбор цели из своих (деп+отдел),
   текст «что сделал». Список вкладов дня показывается в том же модале.
4. **Карточка цели**: описание, родительская цель, хроника вкладов (кто/когда/что),
   история переносов.
5. **Закрытие периода** (режим страницы «Стратегия», доступен director/admin):
   мастер по целям департамента — для каждой выбрать done / partial / dropped,
   для не-done «почему» обязательно; чекбокс «перенести в следующий период»;
   тут же — постановка целей нового периода. Это и есть подготовка/итог квартальной встречи.

## 8. Этапность

- **Фаза 1 (MVP)**: модель + миграция, CRUD с RBAC, страница «Стратегия» (текущий период,
  без закрытия), виджет ЛК, вклад из DayModal. Тесты роутов (RBAC-гарды, инварианты периода).
- **Фаза 2**: закрытие периода (мастер, переносы, событие встречи в календаре),
  прошлые периоды read-only, маркеры переносов.
- **Фаза 3**: связь Tasks↔цели, чат по цели, уведомления/дайджесты, срез в аналитике.

## 10. Рабочая таблица квартальной встречи (артефакт Влада, 2026-08-08)

Сейчас цели ведутся в таблице-Excel. **Строки сгруппированы по департаментам (~8); внутри некоторых департаментов — под-строки отделов** со своими записями. На **ежеквартальной встрече руководители работают прямо с этой таблицей** (ставят/закрывают/подводят итоги). Задача: перенести этот процесс в Nexus так, чтобы (а) руководители заполняли её у нас, (б) цели/задачи **автоматически ставились в отделы**, (в) **департамент видел все задачи, которые «висят» над его отделами** (roll-up), (г) у записей были состояния (не просто текст).

**Столбцы таблицы → маппинг на модель:**

| Столбец | Смысл | Маппинг |
|---|---|---|
| План на II квартал | цели, поставленные на квартал | `StrategicGoal` periodKey=`2026-Q2`, horizon=quarter, status=active |
| Реализованное | итог квартала: что сделано | те же цели Q2 после закрытия: status=`done` (+`outcome`) |
| Нереализованное | итог: не сделано + почему | цели Q2: status=`partial`/`dropped` + `outcome` (обяз.) |
| План на III квартал | цели следующего квартала | `StrategicGoal` periodKey=`2026-Q3` (часто — перенос `carriedFromId`) |
| План на год, зоны роста | годовые направления/зоны роста | `StrategicGoal` horizon=year (+ отдельная пометка «зона роста») |
| Доработки к собранию | заметки к встрече | заметка периода/отдела (поле или мини-сущность `MeetingNote`) |
| Цели 2026 | годовые цели | `StrategicGoal` horizon=year, periodKey=`2026` |
| Комментарии | комментарии | заметка (то же, что «Доработки») |

Вывод: **таблица — это МАТРИЦА представления** `StrategicGoal` (строки = департамент/отдел, столбцы = периоды/итоги/заметки), а квартальная встреча = режим её заполнения+закрытия (§6.5). «Реализованное/Нереализованное» — не отдельные поля, а срез статусов закрытого квартала. Это ложится на модель §3; добавляется лишь: заметки к собранию (Доработки/Комментарии) и явная пометка «зона роста».

**Каскад задач (уточнение к §7 «Задачи»):** цель департамента → цели/задачи отделов (`parentGoalId`); отдел видит свои, департамент — все под ним (roll-up). `Task.goalId` (заготовка в схеме) → оперативные задачи по цели автоматически попадают в отдел-владелец; департамент видит все задачи над отделами. Это **Фаза 3** (связь Tasks↔цели) — ядро запроса Влада «задачи автоматически ставятся в отделы».

**Данные:** реальные ~8 департаментов (и их отделы) на тестовом сервере удалены при ре-сиде — восстановить/пересоздать структуру перед наполнением.

**Соотношение с блоком «Цели компании» на Пульсе:** нынешний `CompanyGoal` (тезисы) — лёгкая витрина «перед глазами у всех», НЕ заменяет этот модуль. Полноценная «Стратегия» — отдельный раздел; блок на Пульсе может позже показывать выжимку из неё.
