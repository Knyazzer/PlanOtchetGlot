# TV Shifts — План реализации

## Общий подход

Разработка ведётся итерационно. Каждый этап — рабочий слой, который можно протестировать до начала следующего. Начинаем с фундамента (инфраструктура + БД + авторизация), заканчиваем аналитикой.

---

## Этап 1 — Фундамент

**Цель**: поднять рабочее окружение, базу данных, авторизацию и базовый CRUD.

### 1.1 Инфраструктура
- [ ] Инициализировать монорепо (pnpm workspaces)
- [ ] Создать `apps/web`, `apps/api`, `packages/db`
- [ ] Настроить TypeScript во всех пакетах
- [ ] Настроить `docker-compose.yml`: PostgreSQL + API + Web
- [ ] Прокинуть переменные окружения через `.env`

### 1.2 База данных
- [ ] Написать Prisma schema (все таблицы из [04-database-schema.md](04-database-schema.md))
- [ ] Запустить первую миграцию
- [ ] Создать seed-скрипт с тестовыми данными (5 пользователей, 3 проекта)

### 1.3 Авторизация (API)
- [ ] POST `/auth/login` — вход, выдача JWT
- [ ] POST `/auth/refresh` — обновление токена
- [ ] POST `/auth/logout`
- [ ] Middleware: проверка роли (employee / admin / producer)

### 1.4 Авторизация (Web)
- [ ] Страница логина
- [ ] Хранение токена в httpOnly cookie
- [ ] Protected routes — редирект на логин если не авторизован
- [ ] Контекст текущего пользователя

### 1.5 Admin-панель — Пользователи
- [ ] GET/POST/PATCH/DELETE `/users`
- [ ] Страница списка пользователей
- [ ] Форма создания/редактирования пользователя (ФИО, email, роль, табельный номер)

**Результат этапа**: рабочий Docker Compose, можно зайти в систему, создать пользователей.

## Этап 2 — Ручные проекты и производственный календарь

**Цель**: базовый производственный календарь с ручным вводом проектов.

### 2.1 Проекты (API)
- [ ] GET `/projects` — список с фильтрами (дата, статус)
- [ ] POST `/projects` — создать вручную
- [ ] PATCH `/projects/:id` — редактировать
- [ ] DELETE `/projects/:id`

### 2.2 Производственный календарь (Web)
- [ ] Интегрировать FullCalendar, недельный вид
- [ ] Отображение проектов на датах
- [ ] Правая панель: неподтверждённые проекты (без даты / с примерным месяцем)
- [ ] Навигация по неделям
- [ ] Цветовая индикация статусов проекта

### 2.3 Детальная карточка проекта
- [ ] Модалка/страница с полной информацией по проекту
- [ ] Список специалистов (пока пустой)
- [ ] Статус и источник данных

**Результат этапа**: работающий календарь, можно вручную создавать проекты и видеть их на неделе.

---

## Этап 3 — Google Sheets синхронизация

**Цель**: автоматический импорт данных из трёх источников.

### 3.1 Базовая интеграция
- [ ] Настроить Google Service Account, добавить ключ в `.env`
- [ ] Создать базовый клиент Google Sheets API (с rate limiting)
- [ ] Утилита для извлечения spreadsheet ID из URL

### 3.2 Парсер таблицы проектов
- [ ] Читать колонки A–I + «Ссылка на матрицу»
- [ ] Читать цвет ячеек → определять `uncertain_fields`
- [ ] Определять статус: `preliminary` / `ready`
- [ ] Upsert проектов в БД по ключу (client + date или sheet row index)

### 3.3 Парсер реестра матриц
- [ ] Читать колонки A–L реестра
- [ ] Извлекать ссылки на матрицы из колонки B
- [ ] Upsert записей `matrix_registry` в БД

### 3.4 Парсер матрицы проекта
- [ ] Читать лист СВОД → получать дату проекта и ID
- [ ] Читать строку 2 листа ₽ СМЕНЫ → получать массив дат
- [ ] Читать строки 4+ → извлекать ФИО, роль, тип занятости, маркеры дней
- [ ] Определять тип смены по позиции колонки
- [ ] Матчить ФИО → user_id (точное совпадение)
- [ ] Upsert `project_assignments` и `shift_entries`

### 3.5 Планировщик
- [ ] node-cron: запускать полный цикл синхронизации каждые 30 минут
- [ ] POST `/sync/trigger` — ручной запуск (для админа и продюсера)
- [ ] Запись в `sync_logs` — статус, количество изменений, ошибки

### 3.6 Обработка edge cases
- [ ] Проект есть, матрицы нет → создать уведомление `no_matrix`
- [ ] ФИО не найдено в users → создать уведомление `unmatched_name`
- [ ] Колонка B реестра — текст, не URL → пропустить, залогировать

**Результат этапа**: проекты и команды автоматически подтягиваются из Google Sheets.

## Этап 4 — Учёт смен и конфликты

**Цель**: подтверждение смен, подсчёт, конфликты.

### 4.1 Смены (API)
- [ ] GET `/shifts` — список смен с фильтрами (user_id, месяц, проект)
- [ ] PATCH `/shifts/:id/confirm` — подтвердить смену (только admin)
- [ ] POST `/shifts` — создать вручную (только admin)
- [ ] PATCH `/shifts/:id` — редактировать (только admin)

### 4.2 Месячный итог
- [ ] POST `/monthly-summaries/:userId/:year/:month/vacation` — добавить дни отпуска
- [ ] GET `/monthly-summaries/:userId` — итоги за период
- [ ] Автоматический расчёт threshold при запросе: `ceil(working_days × 16/22)`

### 4.3 Конфликты на календаре
- [ ] API: GET `/conflicts?dateFrom=&dateTo=` — найти пересечения (один user, две смены в один день)
- [ ] Web: подсветка конфликтов на календаре
- [ ] Карточка конфликта с возможностью переназначить сотрудника

### 4.4 Diff UI (конфликт данных при синхронизации)
- [ ] При upsert: сравнивать входящие данные с существующими записями с `source = manual`
- [ ] Если расхождение → создать запись в `notifications` с типом `data_conflict`
- [ ] Web: панель разрешения конфликтов — показать diff, кнопки «Принять наше» / «Принять их»

### 4.5 Страница сотрудника
- [ ] Мой календарь (личные смены за месяц)
- [ ] Счётчики: итого смен / минимум / переработка / отпуск
- [ ] Лог изменений расписания

**Результат этапа**: полный учёт смен, видны переработки и отпуска, конфликты подсвечены.

---

## Этап 5 — Уведомления и логи

**Цель**: система уведомлений и полная история изменений.

### 5.1 Уведомления
- [ ] GET `/notifications` — список для текущего пользователя
- [ ] PATCH `/notifications/:id/read` — отметить прочитанным
- [ ] Web: колокольчик в шапке, бейдж с количеством непрочитанных
- [ ] Дроп-даун с группировкой по типам уведомлений

### 5.2 Change log
- [ ] Middleware/хук в Prisma: записывать изменения в `change_logs` при update
- [ ] GET `/change-logs?entityType=&entityId=` — история по сущности
- [ ] Web: лог в карточке проекта и в профиле сотрудника
- [ ] Web: глобальный лог в admin-панели с фильтрами

**Результат этапа**: все изменения отслеживаются, сотрудники видят что изменилось в их расписании.

---

## Этап 6 — Бэклог задач

**Цель**: простой task tracker для команды.

- [ ] GET/POST `/tasks` — список и создание (admin)
- [ ] PATCH `/tasks/:id` — редактирование
- [ ] POST `/tasks/:id/assign` — взять задачу (employee)
- [ ] PATCH `/tasks/:id/complete` — завершить
- [ ] Web: страница бэклога — список с фильтром по статусу
- [ ] Web (admin): кто взял задачу, когда завершил

**Результат этапа**: команда может видеть задачи и брать их в работу.

---

## Этап 7 — Дашборды и аналитика

**Цель**: отчётность по сменам и задачам.

- [ ] API: GET `/analytics/shifts` — смены по пользователям за период
- [ ] API: GET `/analytics/projects` — проекты с составом команды
- [ ] Web: дашборд администратора:
  - Таблица смен по сотрудникам за месяц
  - Переработки / отпуска
  - Кто на каких проектах участвовал
  - Выполненные задачи
- [ ] Фильтры: период, сотрудник, проект

**Результат этапа**: полная аналитика для руководителя.
