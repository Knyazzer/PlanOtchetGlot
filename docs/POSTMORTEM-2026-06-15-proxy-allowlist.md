# Post-mortem: белый экран на половине страниц после деплоя rebuild-v4 в прод

> **Дата инцидента:** 2026-06-14 — 2026-06-15
> **Затронуто:** прод `nexus.megapolis.media` (`nexus.knzteam.ru`), страницы Мой кабинет, Свод, Аналитика, Настройки
> **Корневая причина:** allow-list API-путей в nginx web-контейнера не содержал новых роутов rebuild-v4 → запросы уходили в SPA-fallback и возвращали `index.html` вместо JSON
> **Время до устранения:** долго — диагностику съели 5 ложных гипотез и параллельные проблемы деплоя
> **Исправление:** 1 строка в [`apps/web/nginx.conf`](../apps/web/nginx.conf) (+ страховочный ErrorBoundary и временный visibility gate)

---

## TL;DR

После выкатки накопленной ветки rebuild-v4 в прод половина страниц падала в белый экран с ошибками `n.find is not a function` и `Cannot read properties of undefined`. Перебрали и **исключили**: баг во фронте, старый образ api, рассинхрон `JWT_SECRET`, непрогнанные миграции, протухшую сессию. Реальная причина оказалась в **reverse-proxy**: nginx web-контейнера проксирует API-пути на `nexus-api` по **жёстко зашитой регулярке-allow-list**, и 6 новых роутов (`day-entries`, `svod`, `analytics`, `board`, `access`, `notifications`) в неё не добавили. Эти пути попадали в `try_files … /index.html` → фронт получал HTML и парсил его как JSON → краш. Лечится добавлением префиксов в регулярку.

---

## Контекст

- Архитектура прода: **web-контейнер** (nginx + собранный SPA) и **api-контейнер** (Fastify) — два отдельных Docker-сервиса за Nginx Proxy Manager.
- Внутри web-контейнера nginx сам решает: путь похож на API → `proxy_pass http://nexus-api:4000`, иначе → отдать `index.html` (SPA-роутинг на клиенте).
- В прод выкатывалась большая ветка rebuild-v4, добавившая новые домены: День/Свод, Аналитику, личные доски, RBAC-гранты, агрегатор уведомлений — то есть **новые API-роуты** `/day-entries`, `/svod`, `/analytics`, `/board`, `/access`, `/notifications`.
- Деплой: push в `master` → GitHub Actions (build образов → GHCR) → SSH на VDS (`git reset --hard origin/master`, `docker compose pull/up`).

## Хронология расследования

Главная ловушка: симптомы выглядели как баг во фронте или рассинхрон данных, и мы долго копали не там. Ниже — каждая гипотеза, что её проверяло и что это дало.

### Шаг 0. Стабилизация, чтобы не диагностировать вслепую

Прежде чем искать причину, сделали два хода, которые потом сами стали диагностическими инструментами:

1. **ErrorBoundary вокруг `<main>` и чата** ([`apps/web/src/components/ErrorBoundary.tsx`](../apps/web/src/components/ErrorBoundary.tsx)). Краш одной страницы перестал ронять всё приложение белым экраном — сайдбар/навигация остаются живыми. Ключевой бонус: boundary **печатает имя упавшей страницы** (`Краш на странице «X»`), что потом локализовало проблему даже в минифицированном проде.
2. **Восстановили visibility gate** ([`apps/web/src/App.tsx`](../apps/web/src/App.tsx)): не-админы видят только кабинет-заглушку (должность + кнопка в Инвентаризацию). Это убрало пользователей с линии огня, пока чиним, и оставило полный (падающий) интерфейс только админу для отладки.

### Шаг 1. Гипотеза «баг во фронте» — частично исключена

Прошли весь путь дефолтной/смонтированной страницы (`AppShell` → `DashboardPage` → `DayFillCard` → `ChatsPage`). Все вызовы `.find`/`.map` стояли на гарантированных массивах (`= []`, `?.`, API-контракт). Статический анализ показал: **при корректном ответе API краша быть не может**. Значит дело в том, что API отдаёт «не то».

**Дало:** перенос фокуса со фронта на рантайм/данные. ErrorBoundary назвал конкретные страницы: Мой кабинет, Настройки, Аналитика, Свод.

### Шаг 2. Гипотеза «ws-token / auth» — частично верна, но не корень

В логах api массово светился `GET /chats/ws-token → 401`. Нашли реальный (пре-существующий) баг: `getWS()` брал ws-токен сырым `fetch(..., {credentials:'include'})` — только кука, без Bearer; в проде куки нет → 401. **Починили** ([`apps/web/src/pages/ChatsPage.tsx`](../apps/web/src/pages/ChatsPage.tsx) → `api.get('/chats/ws-token')`).

**Дало:** убрало шум 401, но белый экран остался. Вывод: 401 — отдельная история, не корень крашей.

### Шаг 3. Гипотеза «старый образ api / рассинхрон версий» — исключена

Подозрение: web новый, а api старый (отдаёт старые формы). Проверили:
- Дата образов: `api 20:52`, `web 20:54` — оба свежие, из одного CD-рана.
- Что реально внутри контейнера:
  ```sh
  grep -c seedSheetConfigsFromEnv apps/api/dist/server.js   # → 0  (новый код: googleapis удалён)
  grep -c effectiveFrom apps/api/dist/routes/day-entries.js # → 7  (новый роут на месте)
  grep -c "map.values" apps/api/dist/routes/day-entries.js  # → 1  (роут отдаёт массив)
  ```

**Дало:** api — **новый код**, отдаёт правильные формы. Гипотеза старого образа/кэша слоёв снята.

### Шаг 4. Гипотеза «JWT_SECRET» — исключена

`401 <1мс` без обращения к БД = падает `jwtVerify`. Проверили:
- В контейнере `JWT_SECRET_len=44` — секрет на месте.
- `sha256(api JWT_SECRET) == sha256(supabase GOTRUE_JWT_SECRET)` — **идентичны**.

**Дало:** api корректно верифицирует токены Supabase. Auth исправен.

### Шаг 5. Гипотеза «непрогнанные миграции / пустая БД» — исключена

Лог старта api: `30 migrations found. No pending migrations to apply.` Схема накатана автоматически (Dockerfile CMD: `prisma migrate deploy`). А пустые таблицы дали бы **пустые массивы**, а не краш (`[].find` валиден).

**Дало:** ни схема, ни сид данных тут ни при чём.

### Шаг 6. Перелом — смотрим РЕАЛЬНЫЙ HTTP-ответ

Когда все «бэкендовые» версии отпали, открыли в браузере **DevTools → Network** на живой сессии:
- **Все запросы 200/304**, `Authorization: Bearer …` присутствует — auth точно работает (прошлые 401 были от мёртвой сессии в фоновой вкладке).
- Кликнули на запрос `/day-entries/formats` → вкладка **Response**:

  ```html
  <!doctype html>
  <html lang="en"><head><title>Nexus</title>
  <script type="module" src="/assets/index-GqKfAsiF.js"></script>
  ...
  ```

**Это и был момент истины.** API-запрос возвращал **`index.html` SPA**, а не JSON. Значит `r.data` = строка HTML → `formats` = строка → `string.find` не функция. Те же грабли для `data.employees` / `.map` / `.slice` на HTML-строке = все 4 краша.

### Шаг 7. Локализация в конфиге

Раз `/day-entries/*` уходит на web, а `/tasks`, `/events`, `/structure` — на api, дело в маршрутизации. Нашли [`apps/web/nginx.conf`](../apps/web/nginx.conf):

```nginx
location ~ ^/(auth|users|tasks|projects|work-items|tracks|clients|events|calendar-entries|chats|database|structure|health)(/.*)?$ {
    proxy_pass http://nexus-api:4000;
}
location / { try_files $uri $uri/ /index.html; }   # SPA fallback
```

Allow-list **жёстко зашит** и не содержит новых префиксов rebuild-v4. Сверка с регистрацией роутов в [`apps/api/src/server.ts`](../apps/api/src/server.ts) показала ровно 6 пропущенных: `day-entries`, `svod`, `analytics`, `board`, `access`, `notifications` — что один в один совпало со списком падающих страниц.

---

## Корневая причина

nginx web-контейнера проксирует на api только пути из **захардкоженной регулярки-allow-list**. Новые роуты rebuild-v4 в неё не добавили, поэтому их запросы попадали в SPA-fallback (`try_files … /index.html`) и возвращали HTML со статусом 200. Фронт парсил HTML как JSON → `TypeError` при первом же `.find`/`.map`/доступе к полю.

Почему так трудно ловилось:
- **200, а не ошибка** — ни в логах api (запрос туда не доходил), ни по статус-коду ничего не подсвечивалось.
- **Часть страниц работала** — их роуты были в списке, что маскировало системность.
- **Параллельные проблемы деплоя** (см. ниже) создавали фоновый шум (401 от мёртвой сессии, denied-pull) и уводили в сторону.

---

## Решение

[`apps/web/nginx.conf`](../apps/web/nginx.conf) — добавили недостающие префиксы в регулярку и комментарий о необходимости держать список в синхроне с `server.ts`:

```nginx
# ВАЖНО: список префиксов ДОЛЖЕН совпадать с register(...) в apps/api/src/server.ts.
location ~ ^/(auth|users|tasks|projects|work-items|tracks|clients|events|calendar-entries|chats|database|structure|health|day-entries|svod|board|analytics|access|notifications)(/.*)?$ {
    proxy_pass http://nexus-api:4000;
}
```

Изменение в web-образе → push в master → CD пересобрал web → задеплоил.

## Верификация

После деплоя и `Ctrl+Shift+R`:
- В Network `/day-entries/formats`, `/svod`, `/analytics`, `/access`, `/notifications` возвращают **JSON массив/объект**, а не HTML.
- Страницы Мой кабинет, Свод, Аналитика, Настройки открываются без рамки ErrorBoundary.

## Сопутствующие проблемы (фоновый шум, тоже устранён)

Эти вещи всплыли по дороге и замедлили диагностику — фиксируем, чтобы не повторять:

1. **`VDS_HOST` секрет не задан** — CD падал на SSH-шаге `Error: missing server host`. IP вынесли в секрет, а сам секрет не завели. Решение: добавить `VDS_HOST` в GitHub Actions secrets.
2. **GHCR pull `denied` на VDS при ручном деплое** — VDS не залогинен в GHCR. CD логинится сам через `GITHUB_TOKEN`; для ручного нужен `docker login ghcr.io` с PAT (`read:packages`).
3. **401 от протухшей сессии в фоновой вкладке** — выглядело как глобальный сбой auth, хотя свежая сессия отдавала 200. Урок: не доверять логам без привязки к конкретной сессии.

## Уроки и профилактика

1. **Allow-list в прокси — хрупкая связь.** Каждый новый роут в `server.ts` требует ручной правки `nginx.conf`. Добавлен комментарий-напоминание; в чек-лист «новый роут» (см. `CLAUDE.md`) стоит внести пункт «добавить префикс в `apps/web/nginx.conf`». Альтернатива на будущее — инвертировать логику: на api проксировать всё, кроме `/`, `/assets/*`, статики.
2. **ErrorBoundary с именем страницы — мощный диагностический инструмент** в минифицированном проде: вместо белого экрана и нечитаемого стека сразу видно, какой раздел упал. Оставлен в коде навсегда.
3. **Смотреть РЕАЛЬНЫЙ ответ по сети раньше.** Полдня ушло на бэкенд-гипотезы; один взгляд в Network → Response (HTML вместо JSON) закрыл вопрос за минуту. При `TypeError` на данных — сначала проверять, что реально пришло по проводу.
4. **`200 ≠ корректный ответ.** SPA-fallback отдаёт HTML с кодом 200 — статус-коды не подсветят такую ошибку. Признак: `… is not a function` / `Cannot read … of undefined` на данных, которые «точно должны быть массивом».
5. **Разделять сигнал и шум.** 401 от мёртвой сессии и denied-pull — отдельные проблемы; их стоило быстро пометить как несвязанные, а не встраивать в основную гипотезу.
