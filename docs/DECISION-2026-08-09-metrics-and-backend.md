> Зафиксировано по итогам разбора моделей расчёта эффективности (`docs/расчет эффертивности ресерч/` — ChatGPT + DeepSeek)
> и изучения архитектуры Huly (self-host). Решения приняты Владом. Это **decision record** — источник правды по обоим вопросам.

## Решение 1 — Метрики сотрудников: только сухие факты, без формул

### Суть решения
Компания **отказывается от любых вычисляемых показателей «эффективности / загрузки»** в продукте. Вместо этого — **сырые факты** по каждому сотруднику, суммы «в лоб», без соотношений и производных формул.

### Что показывать сотруднику (личный кабинет / аналитика)
Только его собственные факты:
- **задач поставлено / выполнено** (счётчики за период);
- **отработано часов** (от старта до конца рабочего дня), **норма**, **переработка** (отработано − норма);
- **время на каждую задачу** (`plannedMinutes` / `actualMinutes`);
- всё — простыми суммами, **без деления, коэффициентов, %-эффективности, рейтингов**.

Никаких математических вычислений и сравнений с коллегами сотруднику не показывать.

### Что убрать
Текущая математика «эффективности / нагрузки» в **`AnalyticsPage`** (вкладка «Эффективность»: `fillPct`, `loadTone`, `score`, нагрузка %) — сделана на скорую руку и **не подходит компании**. Убрать вычисляемые показатели из UI.

### Что обязательно СОХРАНИТЬ
**Чистые источники данных не удалять** (поля, сбор, заполнение) — это фундамент под будущую бизнес-аналитику/KPI на **живых данных** (разные модели можно будет примерять позже, когда накопится история). Уже есть: `Task.plannedMinutes/actualMinutes`, `DayEntry`, `Task.startDate/finishedAt`, счётчики задач, `Task.goalId` (привязка к целям — «ценность» живёт там, а не вычисляется из часов).

### Область применения
**Офисные / задачные департаменты (бэк-офис)** — продажи, HR, дизайн, администрация и т.п.
**ТВ-эфирная бригада считается по производственным сменам — это отдельная модель**, к задачным метрикам не относится.

### Обоснование
Ресёрч (две независимые модели) сошёлся: единой честной «эффективности сотрудника» не существует (закон Гудхарта — метрика-цель перестаёт быть метрикой). Любая формула (в т.ч. интервальная `1/k`, `работа/отработано`) либо геймится, либо измеряет не то (напр. `работа/отработано ≈ k` — среднюю одновременность, а не продуктивность). Правильный путь — сначала копить **честные сырые данные**, модели примерять потом на реальной истории. Полный разбор — `docs/расчет эффертивности ресерч/`.

### Задача для реализации (Nexus-чат)
- Вырезать вычисления эффективности/нагрузки из `AnalyticsPage`; сбор данных оставить.
- Личный кабинет: блок «сухих фактов» по сотруднику (счётчики + часы/норма/переработка + время по задачам).
- Ничего не сводить в единый балл, не выводить на премию/публичную доску.

## Решение 2 — Бэкенд: профессиональные ПАТТЕРНЫ, не переписывание

### Факт-чек текущего стека (важно)
Бэкенд Nexus — **НЕ «чистый JS + Express»**. Сейчас: **Fastify + TypeScript + Prisma + PostgreSQL**, Zod (`safeParse`) на границах, Supabase Auth (JWT), WebSocket-хаб. Это уже профессиональный, типобезопасный стек. Переписывать «на серьёзное» с нуля не требуется.

### Как обрабатывает данные Huly (методы, зафиксировано из `huly-selfhost/ARCHITECTURE_OVERVIEW.md`)
- **Единый путь записи через сервис-транзактор**: все мутации = транзакции; транзактор применяет бизнес-логику → пишет ACID-транзакцию в БД (CockroachDB) → публикует событие в очередь (Redpanda/Kafka) → броадкастит изменение живым клиентам по WS.
- **Событийный поток**: транзактор → очередь → потребители (напр. полнотекстовая индексация). Асинхронная обработка развязана.
- **CRDT (Y.js)** — совместное редактирование документов без конфликтов.
- Целостность защищена тем, что **никто не пишет в БД в обход транзактора** (иначе рассинхрон индексов/клиентов).

### Что забрать (паттерны, НЕ движок)
- **ACID-транзакции вокруг многошаговых записей** (`prisma.$transaction`) — критично для **финансовых проводок** (модель `Expense`, бюджеты `WorkItem`): либо всё, либо ничего.
- **Append-only аудит / событийный лог** — неизменяемость истории (принцип экосистемы «прошлое не меняется»). Даёт аудит + аналитику задним числом на любую дату.
- **Outbox-паттерн** — надёжная доставка событий во внешние сервисы (пригодится для «Nexus как слой сведения», `docs/ECOSYSTEM-AGGREGATION.md`).
- **Единый write-path / сервисный слой** + оптимистическая блокировка / версионирование строк (консистентность при параллельных правках).
- Для финансов — **журнал типа двойной записи**, immutable-записи, сверка.

### Чего НЕ тащить
Полный **event-sourcing + транзактор Huly, Kafka, CRDT** — избыточно для масштаба (внутренняя платформа на тысячи пользователей, не миллионы tx/сек) и противоречит философии простоты. Тяжёлые фреймворки (NestJS для структуры, Temporal для саг/воркфлоу, Kafka для стриминга) — вводить **только под конкретную доказанную потребность**, не превентивно.

### Вывод
Фундамент (**Postgres + Prisma + TS + Fastify**) — оставляем, он профессиональный. «Профессиональность» для критичных бизнес-данных и проводок достигается **паттернами** (ACID-транзакции, аудит-лог, outbox, ledger двойной записи), а **не сменой фреймворка и не переписыванием**. Это дёшево, безопасно и совместимо с текущим стеком.
