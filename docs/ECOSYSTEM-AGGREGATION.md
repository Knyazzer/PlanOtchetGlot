# ECOSYSTEM-AGGREGATION — Nexus как слой сведения экосистемы (фундамент)

> Статус: **фундамент-документ (архитектурное направление), согласован с Владом 2026-07-28.**
> Это НЕ план реализации и НЕ фича к немедленной стройке. Цель — зафиксировать
> направление «экосистема через обмен данными» и дать команде по техдолгу список
> «что заложить сейчас / чего не хардкодить», чтобы будущая агрегация не стала ретрофитом.
> Идентичность/SSO — уже есть, см. [INTEGRATION.md](INTEGRATION.md); этот документ — **следующий слой**.

## 1. Зачем

Сегодня экосистема Megapolis связана **только идентичностью** (`public.users` + единый вход через
портал Nexus). Обмена бизнес-данными между продуктами нет by design (схемная изоляция).
Следствие: сотрудник работает в разных продуктах (Nexus, support, kanban…), у каждого свои
задачи/чаты/уведомления, и **нигде нет единой картины его загрузки**; чтобы отчитаться за день,
надо пройтись по нескольким системам и переписать руками. Это «продукты с общим аккаунтом», а не
экосистема.

**Цель:** Nexus — **единый кабинет**, где сотрудник видит все свои задачи и загрузку, а руководитель
— реальную загрузку людей. Тяжёлый функционал остаётся в продуктах; Nexus **сводит** данные из них.

## 2. Принцип высот (ключевое разделение)

- **Продукт (support, kanban, будущие) = глубокое рабочее место.** Весь тяжёлый специфичный
  функционал (канбан на 6 столбцов, тикеты, SLA…). **Саму работу делают внутри продукта.**
- **Nexus = слой сведения (не дубль воркспейса).** Единая картина: список всех задач, загрузка,
  план-отчёт, «что у меня висит и откуда». Другая **высота** — обзор + консолидация, а не повтор
  функционала. По внешней задаче в Nexus **не работают** — при попытке правки Nexus
  **перебрасывает в исходный продукт** (deep-link).
- Для **лёгких** задач (сам себе, проектные без своего продукта) Nexus и есть рабочее место.
  Для **тяжёлых** (kanban/support) — зеркало + ссылка.

Nexus покрывает ~90% компании; в отдельные продукты выносится только то, что требует глубокого
решения конкретной бизнес-задачи.

## 3. Модель обмена данными

- **Источник правды — продукт.** Nexus **зеркалит** статус/состояние чужой задачи (read-only) и
  показывает в списке сотрудника; мастер-данные и правку держит продукт.
- **Push, событийно.** Продукт сам шлёт «событие произошло» → Nexus. Nexus **не опрашивает** продукты.
- **Сервис-сервис контракт (новый слой поверх SSO):**
  - у каждого продукта — свой **service-account / API-ключ**;
  - продукт по HTTP шлёт в **приёмный эндпоинт Nexus** стандартный **конверт события**;
  - это **не новый сервер** — это **коннектор внутри каждого продукта** («при событии → POST в
    Nexus») + одна приёмная точка в Nexus.
- **Схемную изоляцию БД НЕ ломаем.** Никто не пишет в чужую схему напрямую — только через API.

```
[kanban] --событие--\
                     >--> [Nexus: приёмный API] --> зеркало задач + счётчик уведомлений
[support] -событие--/
```

## 4. Канон «рабочей единицы» (унифицированная модель)

Единая форма, к которой приводятся и **внутренние** задачи Nexus, и **внешние** (kanban/support).
Внешняя агрегация — частный случай этой модели.

**Что считаем рабочей единицей:** объект, где сотрудник **создатель** (контролирует) **или
исполнитель** (выполняет). Сообщение в чате, смена статуса — это **уведомление**, НЕ рабочая единица.

**Виды (`kind`):**
- **Задача** — сам себе · назначенная (A→B) · проектно/трековая · **внешняя-зеркало** (kanban/support).
- **Встреча** (летучка) — фиксация рабочего времени, не задача; трек не обязателен.
- **Мероприятие/событие** (ТВ: съёмка/эфир/монтаж…) — **ОТЛОЖЕНО** (см. §10).

**Поля канона (концептуально):**
- `source` — откуда (nexus | kanban | support | …);
- `externalId`, `externalUrl` — id и ссылка на задачу в продукте (для зеркала и deep-link);
- `kind` — задача | встреча;
- `role` относительно сотрудника — создатель | исполнитель;
- `status` — статус-ЖЦ (продукт-агностичный: например `todo | in_progress | done`; многостадийность —
  как под-состояния, не как «за день не закрыто»);
- даты: дата задачи, дедлайн;
- **занятость/время** (nullable, на будущее): плановая/фактическая длительность, от–до;
- привязка к **треку/проекту** (опционально).

**Как разное ложится в одну форму:**
- **kanban-задача (5–6 столбцов, тянется днями)** — одна рабочая единица «в работе», растянутая по
  датам; стадии = под-состояния; при необходимости разбивается на дневные под-этапы (§8).
- **support-тикет** — рабочая единица `kind=задача`, `source=support` («прилетел тикет — обработать»).
- **сам-себе / проектная** — внутренняя задача Nexus в той же форме.

## 5. Время и занятость

- **Назначенная задача (A→B):** авто-хронометраж — цель (взял в работу → пошло время, закрыл → стоп).
  Руками ничего не вписывать.
- **Сам-себе задача:** ручной ввод времени, опционально (личный буфер).
- **Не форсировать** поштучный ввод времени начала/конца по каждой задаче — при 50 задачах в день это
  вызовет отторжение. **Простота важнее полноты.**
- **Производственный календарь занятости** (с какого по какое время что делает сотрудник) — **целевое
  видение**, не сейчас. Сейчас — только **заложить поля** (nullable), не строить.

## 6. Уведомления

- **Сейчас — только счётчик-бейдж на продукт** («в support 3») = маршрутизация внимания, куда сходить.
  Не требует общей модели задач, делается независимо.
- **Текстовый агрегированный инбокс уведомлений** (с содержимым «что произошло») — **позже**, но
  **зафиксировано как нужное**.
- **На почту уведомления не шлём** — не нужно.
- Источник уведомления может быть **внешним** (из продукта), не только из своих `TaskLog`.

## 7. Треки и проекты

- **Опциональная группировка** над задачами. **Не** ограничиваем создание задач без трека.
- **Норма (не жёсткое правило):** при заведении задачи стараемся привязать её к **треку/проекту**
  или к чему-то, в рамках чего она выполняется.
- **Встречи** и разовые **личные/технические** задачи трека могут не иметь; для них допустим
  «личный/разное» контекст.
- Трек — сильная сущность (у сотрудника несколько: проектный, внутренние работы, обучение…);
  может быть личным (следить за этапами) или на нескольких людей (регулярные встречи, стратегия).
  **Развитие треков — отдельный трек работ.**

## 8. План-отчёт — целевая эволюция (отдельный трек, НЕ сейчас)

Направление (описано, чтобы не заложить несовместимого):
- **Отчёт за день генерируется автоматически** из активности сотрудника, а не пишется руками.
- **Единый список задач:** сам себе + назначенные + проектно/трековые + **внешние-зеркала** + встречи —
  всё в одном месте, с видимым источником, сроками, приоритетом.
- **Иерархия:** большая задача («сделать лендинг») → **дневные под-этапы**, которые сотрудник сам
  планирует и цепляет к большой; по ним фиксируется, **что сделано в конкретный день** (не бинар
  «сделано/нет»).
- Незакрытое в конце дня — **переносится/делится**, засчитывается то, что реально сделано за день.
- Внешние рабочие-единицы **автоматически засчитываются** в день/свод (чтобы не переписывать руками).

## 9. Что заложить ПРЯМО СЕЙЧАС (для команды по техдолгу)

Модель **не перестраиваем** — техдолг-чат закрывает долги. Но с оглядкой на два коротких списка.

### (А) Аддитивные заготовки — что безопасно добавить впрок («пустые розетки»)
- На модели задачи (`Task`) — **nullable-поля**: `source`, `externalId`, `externalUrl`, `kind`
  (`task | meeting`), поля времени/занятости. Сегодня пустые, ничего не ломают; потом есть куда класть
  без болезненной миграции на живой системе.
- Уведомления — заложить, что **источник может быть внешним** (не только свои `TaskLog`).
- Предусмотреть **каркас service-account аутентификации** (сервис-сервис вход для приёмного API).
  Реализовывать не обязательно — не закрывать себе такую возможность.

### (Б) Грабли — чего НЕ делать («не заливать бетоном будущее»)
- **Не делать жёсткую ручную схему отчёта** (две колонки «сделано/нет» в отдельной таблице) — это
  заблокирует авто-генерируемый иерархический отчёт (§8). **Свод/отчёт оставить ВЫЧИСЛЯЕМЫМ из задач**
  (как сейчас).
- **Не хардкодить уведомления как «только из своих TaskLog»** — внешним будет некуда встать.
- **Не завязывать задачу жёстко на «один день / бинар сделано»** — задача может тянуться днями и иметь
  под-этапы.
- **Не ломать схемную изоляцию БД** — никаких cross-schema записей; обмен только через будущий API.

## 10. Явно ВНЕ фундамента (отложено, упоминаем — не проектируем)

- **Стройка** эволюции план-отчёта (§8) — отдельный трек.
- **Движок агрегации + продуктовые коннекторы** (сам приём/зеркалирование из kanban/support) — после
  готовности контракта и продуктов.
- **Сквозные чаты** между продуктами — самый тяжёлый трек; отдельная документация.
- **ТВ-департамент / мероприятия / производственный календарь эфирных бригад** — сильно другая модель
  (продюсеры строят занятость, штат+фриланс, участники эфиров). База — план-отчёт **PlanOtchetTVonly**.
  Отдельное обсуждение **после** готовности базы; сейчас не погружаемся.

## 11. Порядок треков дальше (роадмап; каждый — свой спек/план)

| # | Трек | Когда |
|---|---|---|
| 0 | Сервис-сервис контракт + приёмный API Nexus (service-accounts, конверт события) | керн, в паре с #1 |
| 1 | Уведомления-счётчик на продукт (единый бейдж в Nexus) | первый сквозной срез |
| 2 | Агрегация задач → единый кабинет + авто-отчёт (канон рабочей единицы, зеркала kanban/support) | после #0/#1 |
| 3 | Сквозные чаты | тяжёлый, позже |
| 4 | Единый хаб / точка входа (плитки продуктов + агрегированный инбокс) | UX-слой поверх 1–3 |

Порядок сознательный: сначала тонкий сквозной срез (контракт + счётчик уведомлений) — доказывает
механизм и даёт пользу; тяжёлое (агрегация задач, чаты, хаб) — следующими заходами.
