# Модель проекта — рабочий документ

> Живой документ для итеративного проектирования структуры. Не финальная документация.

---

## Проблемы, которые нужно решить

1. **Таксономия форматов** — «Продакшн» это съёмка, монтаж и моушн одновременно; «Телерадио» это TV + Radio; нет единого словаря
2. **Когда рождается проект** — сейчас матрица = договор, но работа начинается раньше
3. **Иерархия** — глобальный проект → задачи → отделы; непонятно за что отвечает каждый уровень
4. **Занятость отделов** — не привязать, пока не стандартизирована структура
5. **Учёт времени** — ручной ввод не работает ни практически, ни аналитически

## Итерация 2 — Уточнённая модель

### Ресторанная аллегория (от пользователя)

```
Клиент платит за весь поход в ресторан  =  Проект (один счёт)
Заказ / блюдо                           =  Work Item (= StatusRow)
Повара которые готовят это блюдо        =  Отделы подключённые к Work Item
Официант который несёт заказ на кухню   =  Продюсер который создаёт Work Item
```

**Work Item = StatusRow** — это одна и та же сущность, просто переименованная для ясности.

### Про «Телерадио» — один Work Item, несколько отделов

Телерадио = **один Work Item**. ТВ и Радио работают одновременно в одном месте:

```
Work Item «Телерадио-шоу, 15 апр, Знаменка»
  Формат: Телерадио
  └── Подключённые отделы (все обязательны):
        ТВ-отдел         → видеотрансляция
        Радио-редакция   → радиоэфир
        Моушн + Дизайн   → заставки для видео
        Радио (доп.)     → джинглы, сценарии, игры со зрителями
```

Вместе застраиваются, вместе выходят в эфир, одна локация. Формат «Телерадио» сигнализирует системе что ТВ-отдел и Радио-редакция **оба обязательны** — нельзя подключить только один.

### ✅ Итерация 3 — Отдел как якорь, тип как метка

```
Work Item
  ├── Название (свободный текст)
  ├── Даты, локация, клиент, статус
  ├── Тип / метка  ← для фильтрации и аналитики, НЕ структурная
  │
  └── Подключённые отделы  ← продюсер выбирает вручную
        Отдел А  [статус: активен / не начат / завершён]
        Отдел Б  [статус: активен / не начат / завершён]
```

**Поток продюсера:**
1. Создаёт Work Item (название + даты + тип)
2. Подключает отделы которые нужны
3. Отделы видят у себя задачу и начинают работу

### Что скрывается под «Продакшн» — 6 разных типов работы

Из реальных названий видно, что «Продакшн» это на самом деле:

```
РЕАЛЬНЫЙ ТИП         ПРИМЕРЫ ИЗ ДАННЫХ
───────────────────  ─────────────────────────────────────────────
Съёмка               Съемка сюжета, Стрит-токи, Съемки на конференции,
                     Сюжет для шоу, Питчинг контент-стратегии
                     → нужна съёмочная группа + выезд

Постпродакшн/Монтаж  Монтаж сериала, Монтаж Люди и Дивизиона
                     → только монтажный отдел, без выезда

Моушн/Анимация       15 минутный моушн 3D ролик, Продакшн моушн ролика
                     → только Отдел моушн-дизайна

Запись/Аудио         Запись песни Магнита, Цупис Подкаст, Подкаст с Рудаковой
                     → студия звукозаписи / аудио отдел

Готовый ролик        Отчётный ролик, Шоурил, Имиджевый ролик, Итоги года
                     → финальный продукт, объединяет съёмку + монтаж + моушн

Промо/Смешанное      ТВ шоу (Продакшн), Фичи, Сочный разговор
                     → съёмка + монтаж + студийная запись вместе
```

### Предлагаемая уточнённая таксономия форматов

Оставить ТВ, Радио, Телерадио, Оффлайн, Менеджмент как есть — они чёткие.
**Разбить «Продакшн» на 3 подтипа:**

```
ФОРМАТ               ОПИСАНИЕ                    ЛОКАЦИЯ
───────────────────  ──────────────────────────  ──────────────────
ТВ                   Прямой эфир / ТВ-шоу        Студия / Выезд
Радио                Радиоэфир                   Романов / Выезд
Телерадио            ТВ + Радио одновременно     Студия / Выезд
Оффлайн              Физическое мероприятие      Знаменка / Выезд
Менеджмент           Координация, не производство —

Съёмка               Видеосъёмка (выезд/студия)  Романов / Выезд
Постпродакшн         Монтаж, цветокоррекция      —  (всегда офис)
Моушн/Анимация       Motion, 3D, анимация        —  (всегда офис)
Подкаст/Запись       Аудиозапись, подкаст        Студия
```

Итоговые ролики/шоурилы — это **результат**, не отдельный формат.
Они возникают как Work Item типа «Съёмка» + потом Work Item «Постпродакшн» в рамках одного проекта.

## 🗺 Итоговая карта системы (все решения)

```
┌──────────────────────────────────────────────────────────────────────────┐
│  ПРОЕКТ  (внешний клиент или сама компания)                              │
│  Клиент · Статус (авто) · Матрица/договор (опционально)                 │
│                                                                          │
│  ┌────────────────────────────────────────────────────────────────────┐  │
│  │  WORK ITEM  (= StatusRow)                                          │  │
│  │  Формат · Дата/дедлайн · Локация (→ конфликт-чек)                 │  │
│  │  Статус авто: Запрос → В работе → Сдан                            │  │
│  │                                                                    │  │
│  │  Отдел А [подключён] → исполнители → задачи у людей               │  │
│  │  Отдел Б [подключён] → ...                                         │  │
│  └────────────────────────────────────────────────────────────────────┘  │
│  Чат проекта (заметки / обсуждение)                                      │
└──────────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────────┐
│  ЗАДАЧА  (универсальный инстанс)                                         │
│  Источник: проект | отдел | кросс-команда                                │
│  Кто поставил · Кому · Дедлайн · Приоритет · ТЗ-вложение · Чат          │
│  Статус: Новая → В работе (timestamp) → Закрыта (timestamp)              │
└──────────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────────┐
│  БРОНЬ СТУДИИ  (не привязана к проекту)                                  │
│  Локация · Дата/время · Цель                                             │
│  → уведомление в профильный отдел → подтверждение/отказ                  │
└──────────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────────┐
│  ФРИЛАНСЕР  (без логина)                                                 │
│  Имя · формат оплаты (за проект / за месяц) · ставка                    │
│  Назначение на Work Item → запрос на оплату → статус оплаты              │
└──────────────────────────────────────────────────────────────────────────┘

ЗАНЯТОСТЬ = событийные дни (Work Items с датой) + фоновые проекты (с дедлайном)
КОНФЛИКТ  = человек или локация в пересекающихся Work Items
НАГРУЗКА  = задач закрыто / активных / просрочено / % в дедлайн

ЛИЧНЫЙ КАБИНЕТ  = сводка дня (горящие → эта неделя → остальное)
                  мои проекты · моя статистика · мои задачи

КАБИНЕТ ПРОДЮСЕРА/РУКОВОДИТЕЛЯ = сводка по всем проектам
                  статус отделов · что требует внимания · что я поставил

КАЛЕНДАРЬ       = авто из Work Items + HR-статусы вручную
                  личный по умолчанию · встречи с кем угодно

ПОРТАЛ ФРИЛАНСЕРА = отдельный вход, только свои задачи и чаты
```

## Итерация 4 — Реальный каталог типов из матриц

Текущие типы из матриц — уже ближайшее к реальности. Сгруппированы в 4 кластера:

```
КЛАСТЕР                 ТИПЫ
──────────────────────  ────────────────────────────────────
Медиапроизводство       Видеотрансляция
                        Телерадиотрансляция
                        Радиотрансляция
                        Подкаст
                        Постановочное видео
                        Отчётный ролик

Мероприятия             Концерт
                        Торжественная церемония
                        Спортивное мероприятие
                        Бизнес мероприятие

Креативные услуги       Аудиопроизводство
                        Видеопроизводство
                        Графический дизайн
                        Моушн-дизайн
                        Оформление эфира
                        Копирайт

Площадки / Event        Аренда площадки
                        Event мероприятие
                        Митап
```

---

### Почему это «сумбурно» — диагноз

Список смешивает **три разных вопроса** в одно поле:

```
ВОПРОС                          ПРИМЕР
──────────────────────────────  ──────────────────────────────
Что мы ДЕЛАЕМ (выход/продукт)?  Видеотрансляция, Подкаст, Ролик
Что это за СОБЫТИЕ?             Концерт, Церемония, Спорт
Какая УСЛУГА оказана?           Моушн-дизайн, Графика, Копирайт
```

Из-за этого:
- «Концерт» и «Видеотрансляция» не исключают друг друга — концерт МОЖЕТ быть трансляцией
- «Моушн-дизайн» это и самостоятельный проект, и подготовительная часть трансляции
- «Event мероприятие» и «Концерт» почти одно и то же

---

### Итерация 4 — Предлагаемое решение: два поля вместо одного

Разделить один перегруженный «тип» на **два независимых поля**:

```
Work Item
  ├── Формат (ЧТО производим / что получит клиент)
  │     Трансляция · Запись/Ролик · Радио/Подкаст · Дизайн/Моушн · Event · Аренда
  │
  ├── Контекст (ЧТО ЗА событие — опционально)
  │     Концерт · Церемония · Спорт · Бизнес · Митап · —
  │
  └── Подключённые отделы (как раньше)
```

**Пример:**
```
Work Item: «Юбилей Газпром»
  Формат:   Трансляция
  Контекст: Торжественная церемония
  Отделы:   ТВ отдел · Технический ТВ · Моушн-дизайн · Саунд

Work Item: «Подготовка айдентики для эфира»
  Формат:   Дизайн/Моушн
  Контекст: —  (самостоятельная услуга, нет события)
  Отделы:   Отдел графического дизайна · Отдел моушн-дизайна
```

**Профит:**
- Аналитика «сколько трансляций за квартал» → по Формату
- Аналитика «сколько концертов обслужили» → по Контексту
- Они не мешают друг другу

## Итерация 1 — Жизненный цикл проекта

```
Запрос (Request)
  │  Клиент прислал бриф / заявку
  │  Отделы могут уже начать превизуализацию, дизайн-концепцию
  ▼
Переговоры (Negotiation)
  │  Обсуждаем условия, бюджет, сроки
  │  Работы продолжаются
  ▼
Согласован (Agreed)
  │  ← ЗДЕСЬ создаётся Матрица / Договор (не раньше!)
  │  Подключаем отделы, назначаем смены
  ▼
Производство (Production)
  │  Активные работы, смены идут
  ▼
Сдан (Delivered)
  │  Закрываем, считаем аналитику
  ▼
[Не согласован / Отменён] — из любого статуса
```

**Матрица (Contract) — опциональный объект на проекте, создаётся при переходе в Agreed.**
До этого момента: проект есть, матрицы нет, работы идут, фиксируются как pre-production.

## Итерация 1 — Занятость отделов

Когда SERVICE_TYPE стандартизирован, занятость считается так:

```
Отдел "Моушн"
  ├─ Проект А / Work Item "Моушн"  →  15-20 апреля  (3 человека)
  ├─ Проект Б / Work Item "Моушн"  →  18-22 апреля  (2 человека)
  └─ Внутренняя задача "Шаблоны"   →  17 апреля     (1 человек)

Занятость на 18 апреля: 5 человек задействованы из X в отделе
```

Не нужен ручной учёт — достаточно назначений на Work Items.

```
Бренд медиа департамент      Отдел бренд медиа
Корп медиа департамент       Отдел корп медиа

Финансовый департамент       Финансовый отдел
Департамент персонала        Отдел персонала
Администрация                Администрация · АХО
```

### Тип департамента

```
ПРОИЗВОДСТВЕННЫЕ (участвуют в Work Items клиентских проектов)
  ТВ · Радио · Дизайн · Бренд медиа · Корп медиа

ПОДДЕРЖИВАЮЩИЕ (участвуют в Work Items по запросу)
  Технический · Спецпроекты

ВНУТРЕННИЕ (работают в канбане / независимых задачах)
  Финансовый · Персонал · Администрация
```

### Специфичные функции по департаментам — V2

Сейчас у всех один общий интерфейс. В будущем отдельные расширения:

```
ТВ департамент         → расширенное планирование (ShiftPlanner), шаблоны проектов
Финансовый департамент → управление бюджетами, подтверждение оплат, финансовые отчёты
Спецпроекты            → CRM-функции (ведение клиентов, воронка сделок)
Технический            → учёт оборудования, выездные комплекты
Персонал               → отпуска, кадровые события
```

Конкретный список функций по департаментам — отдельное обсуждение когда базовая модель готова.

### Что из этого следует для модели

**1. Дублирование в текущих данных — норма, не баг.**
«Технический департамент» и «Технический отдел» это одно. «Технический отдел ТВ» — другой.
Нужно единое мастер-справочник отделов, и маппинг старых названий на него при синке.

**2. Производственные кластеры — это и есть естественные «типы» Work Item.**
Вместо жёсткого enum достаточно дать продюсеру выбрать из кластеров при подключении отделов:

```
Продюсер создаёт Work Item "Трансляция юбилей Газпром 20.05"
  → Нажимает "Подключить отдел"
  → Видит список кластеров:
      ТВ производство  [ТВ отдел, Технический отдел ТВ]
      Радио            [Радио редакция, Музыкальная редакция]
      Постпродакшн     [Видеомонтаж]
      Моушн            [Моушн-дизайн]
      Звук             [Саунд-дизайн]
      Дизайн           [Графический дизайн]
      ...
  → Выбирает ТВ производство + Моушн + Звук
  → Три отдела видят Work Item у себя
```

**3. Внутренние отделы** работают независимо через канбан.
Если Финансовый или АХО иногда участвуют во внешних проектах — их можно подключить вручную, это не ломает модель.

Work Item имеет **два поля**:

```
                                                    Муз. редакция — опционально
Съёмка              Видеосъёмка (монтируется потом) Съёмочная группа
Постпродакшн        Монтаж, цвет, сведение          Монтаж
Моушн/Анимация      Motion graphics, 3D, анимация   Моушн-дизайн
Аудио/Подкаст       Студийная запись, подкаст       Саунд-дизайн / аудио
Дизайн              Графический дизайн, айдентика   Дизайн
Event               Компания организует мероприятие Спецпроекты
Менеджмент          Координация, без продукта       —
```

```
КОНТЕКСТ (опционально)     КОГДА ИСПОЛЬЗУЕТСЯ
────────────────────────── ──────────────────────────────────────────
Концерт / Шоу              Трансляция или съёмка концерта

Конференция / Форум        Деловое мероприятие
Спортивное мероприятие     Спорт
Митап / Встреча            Небольшое мероприятие
Фестиваль                  Фестиваль
Другое [+ текст]           Редкие случаи

```

**Пример:**
```
«Трансляция концерта Газпром 20 мая»

«Моушн-ролик для рекламы»
```

## ✅ Поток отделов — зафиксированные решения

### Кто назначает исполнителей
```
Продюсер → подключает отдел к Work Item
Руководитель отдела → назначает конкретных людей (основной путь)
Продюсер → тоже может назначить (с пометкой кто поставил задачу)
```

### Статусы Work Item — двуосевая модель

**Ось 1 — Жизненный цикл WI (видно на карточке, управляет продюсер):**
```
Заявка       WI создан; отделы подключены, задачи описаны кратко
             Детали могут меняться после встреч с заказчиком
               │  ручной переход — продюсер, после детализации
               ▼
Реализация   Задачи детализированы по отделам, работа идёт в полную силу
               │  авто-переход — когда все отделы = «Завершён»
               ▼
Сдан         Все отделы завершили участие → WI закрыт (автоматически)
```

**Ось 2 — Подстатус каждого подключённого отдела (параллельно, независимо):**
```
Не начат   →   В работе   →   Завершён
```
- «В работе»: авто — первая задача взята сотрудником (или первое назначение в ShiftPlanner для ТВ)
- «Завершён»: вручную руководителем (для ТВ — авто по дате последней смены)

WI переходит в «Сдан» **автоматически** когда ВСЕ отделы = «Завершён».

**Видимость задач — ключевое правило:**
```
WI «Заявка»      → продюсер создаёт и редактирует задачи для отделов
                   ОТДЕЛЫ ЗАДАЧИ НЕ ВИДЯТ (работа ещё не опубликована)

WI «Реализация»  → все задачи становятся видны отделам одновременно
                   Момент перехода = «публикация» задач
                   Отделы берут задачи в работу
```

### Что видит сотрудник (личный кабинет)

```
МОИ ЗАДАЧИ
  ├─ Активные (назначены мне, в работе)
  ├─ Входящие (новые, ещё не взятые)
  └─ Завершённые (история)

МОИ ПРОЕКТЫ
  └─ Список Work Items в которых я участвую

КТО ПОСТАВИЛ / КОГДА
  └─ Аудит назначений (продюсер или руководитель)

МОЯ СТАТИСТИКА
  ├─ Закрытых задач за период
  ├─ Проектов за период
  └─ [учёт времени — см. отдельный блок]
```

## Итерация 6 — Блок: Календарь и занятость

### Текущее состояние (хаос)

Сейчас занятость размазана по двум системам:
1. **Корпоративный календарь** — ~20 категорий, видит вся компания, перегружен
2. **Матрицы в Google Sheets** — смены конкретных людей, включая фрилансеров

### ✅ MM / OG — закрыто

MM = вся компания. OG = CEO (один человек).
В новой системе дублирования нет — CEO это просто пользователь с ролью и своим календарём, как все остальные.

### Анализ 20 категорий календаря

Они решают **три разных задачи**, смешанных в одном месте:

```
ЗАДАЧА 1 — Бронирование ресурсов (где работаем)
  Радиостудия, Телестудия, Нижняя студия, Знаменка, Нижняя аудиостудия
  → Это не «событие», это «помещение занято»

ЗАДАЧА 2 — HR-статус сотрудника (где человек)
  Отпуск, Удалёнка, Больничный, Командировка, Отгул, День рождения
  → Влияет на доступность для задач

ЗАДАЧА 3 — Тип события (что происходит)
  Встреча, Выездное мероприятие, Виртуальный эфир, Тендер, Общая встреча
  → Описание самого события
```

### Что можно убрать руками (автоматизировать)

Если Work Items заведены в системе — большинство «событийных» записей в календаре **генерируются автоматически**:

```
Work Item «Трансляция Graduate Awards, 19 фев, Знаменка чёрная»
  → автоматически создаёт событие в календаре отдела ТВ
  → автоматически блокирует «Знаменка чёрная» как ресурс

Сотрудник назначен на этот Work Item
  → в его личном календаре появляется событие на 19 фев
  → больше не нужно вручную вносить в общий календарь
```

Остаётся вносить вручную только **HR-статусы** (отпуск, болезнь, удалёнка).

### Предлагаемая упрощённая структура календаря

Вместо 20 категорий — 3 слоя:

```
СЛОЙ 1 — ПРОИЗВОДСТВЕННЫЕ СОБЫТИЯ (из Work Items, автоматически)
  Генерируются из системы, отображаются в календаре отдела

СЛОЙ 2 — HR-СТАТУСЫ (вручную, личные)
  Отпуск · Больничный · Удалёнка · Командировка · Отгул
  Видны руководителю отдела и системе для расчёта занятости

СЛОЙ 3 — ВСТРЕЧИ (вручную, через систему задач)
  Внутренние встречи создаются как задачи → появляются в календаре
```

### Как это решает занятость

```
Занятость сотрудника на дату X =
  Work Items (назначен, дата попадает в диапазон)
  + НЕТ HR-статуса блокирующего день

Занятость отдела на неделю N =
  Количество активных Work Items × назначенных людей
  с учётом кто в отпуске/на больничном
```

Никакого ручного учёта времени не нужно для базовой занятости.

## ✅ Фрилансеры — зафиксировано

Фрилансер = имя в системе **без логина**. Карточка фрилансера содержит финансовый блок:

```
Фрилансер
  ├── Имя
  ├── Тип оплаты: за проект | за месяц
  ├── План  — рыночная ставка (справочник ставок, пока не реализован → вводится вручную)
  └── Факт  — договорная ставка (на сколько договорились)
```

**Расчёт выплаты — всегда из Факта:**
```
Тип «за месяц»   → сумма по всем WI в которых участвовал за этот месяц
                   = одна сводная выплата в конце месяца

Тип «за проект»  → итог считается отдельно для каждого Work Item,
                   два режима на выбор:
```

**Два режима расчёта «за проект»:**

```
ПРОСТОЙ РЕЖИМ — для событийных WI (ТВ-трансляции, съёмки, эфиры)
  WI имеет чёткие смены (застройка / эфир / демонтаж)
  
  Факт-ставка × количество смен в WI = итог на WI
  
  Пример:
    Вася-оператор, ставка 5 000 ₽/смена
    WI «Трансляция 20 мая» = 2 смены
    Итог: 10 000 ₽


ИТОГОВАЯ СУММА — для фоновых WI (Моушн, Дизайн, Постпродакшн и др.)
  WI не имеет дискретных смен, только диапазон дат
  
  Руководитель вводит итоговый Факт за WI = договорная сумма целиком
  
  Пример:
    Маша-моушн, WI «Анимация заставок» (2 недели)
    Факт: 40 000 ₽ (вся работа, договорная)


РАСШИРЕННЫЙ РЕЖИМ — для многосуточных трансляций с чередованием смен
  Используется когда внутри WI сотрудники чередуются по часам
  (например: трансляция длится сутки, но каждый работает свою смену)
  
  → Активируется почасовой планировщик (ShiftPlanner)
  → Строится детальный график: кто работает с HH:MM до HH:MM
  → Итоговая сумма фрилансера вводится вручную в карточке планировщика
  
  Пример:
    Трансляция 20–21 мая (26 часов)
    Вася работает: 20 мая 20:00 → 21 мая 08:00 (ночная смена)
    Итог: 15 000 ₽ (фиксированная договорная сумма)
```

Переключение между режимами — на уровне конкретного WI (не глобально).

**Запрос на оплату** — задача в бухгалтерию с предзаполненными полями:
```
  Фрилансер: Вася-оператор
  Сумма:     25 000 ₽
  Тип:       за проект
  Режим:     простой / расширенный
  За что:    Work Item «Трансляция 20 мая», проект «Юбилей Газпром»
```

**Аналитика:** сколько проектов / план vs факт по ставкам / выплачено / ожидает оплаты.

## ✅ Конфликты ресурсов — зафиксировано

Конфликт = **один и тот же человек или одна и та же локация назначены дважды в пересекающееся время**.

```
Work Item A: Трансляция, 15 апр, 14:00–18:00, Знаменка чёрная
Work Item B: Трансляция, 15 апр, 16:00–20:00, Выезд

Если Иванов назначен на оба → КОНФЛИКТ (красный маркер)
Если Знаменка чёрная в обоих → КОНФЛИКТ (локация занята)
```

**Отделы и конфликты:**
Разные отделы обычно работают с разными людьми → конфликт возникает только если _одного и того же человека_ назначили в двух разных WI одновременно. Пример: «Монтаж ролика» и «Съёмка» — разные отделы, разные исполнители, конфликта нет. Но если один оператор назначен и на монтаж, и на съёмку в один день — система предупреждает.

**Многодневные фоновые WI** (без конкретных часов, только диапазон дат):
— Не являются жёстким блокером — это **нагрузка**, а не временной слот
— Оба WI отображаются в интерфейсе назначения, визуально видно загруженность человека
— Жёсткий конфликт — только когда оба WI имеют конкретное время и оно пересекается

Система **предупреждает** при назначении, не запрещает жёстко (продюсер может переназначить).

## ✅ Внутренние проекты и бронирование студий

### Ключевой инсайт: всё что занимает ресурс — это либо Work Item, либо Бронь

```
ТИП                    ПРИМЕР                           ПОЛНЫЙ ЦИКЛ?
─────────────────────  ───────────────────────────────  ────────────
Внешний проект         Трансляция для Газпрома           ✅ да
Внутренний проект      Офлайн митап с трансляцией        ✅ да (клиент = компания)
Простая бронь          Внутренняя встреча в Знаменке     ❌ нет (только слот)
```

Разница не в том «внешний или внутренний», а в том **нужен ли производственный процесс с отделами**.

### Модель: единая точка входа

```
Продюсер / руководитель отдела создаёт:

  [Проект/Work Item]                    [Бронь студии]
  Формат · Дата · Локация               Локация · Дата · Время · Цель
  → Полный цикл (отделы, статусы)       → Просто блокировка слота
         │                                       │
         └───────────────────┬───────────────────┘
                             ▼
            Система видит: студия занята в это время
            Конфликт если кто-то пытается взять то же время
```

### Механика бронирования студий — авто-апрув

Ответственный за студии = **Руководитель ТВ отдела** (единая точка контроля).

**Базовое правило: авто-апрув с визуальным статусом**
```
Запрос на студию → слот свободен? → ДА → бронь создаётся автоматически
                                  → НЕТ → уведомление: конфликт по времени
```
Ручного «подтверждения» каждой брони нет. Если слот свободен — заявка проходит автоматически.

**Визуальный статус брони в календаре:**
```
WI в статусе «Заявка»      → бронь отображается как «Предварительно»
                               визуально отличается (прозрачность, штриховка, другой цвет)
                               сигнал: дата/студия могут измениться
WI в статусе «Реализация»  → бронь «Подтверждено», стандартный вид
```
При смене даты WI (на стадии Заявка) — бронь переносится автоматически.

**Руководитель может ЗАБЛОКИРОВАТЬ студию целиком:**
```
Руководитель ТВ → «Закрыть Знаменку чёрную» → причина (ремонт / техработы)
→ Все попытки добавить мероприятие → попап: «Студия закрыта. Причина: ...»
→ Руководитель снимает блокировку → студия снова доступна
```

**Желаемый V2: два уровня доступа к студии**
```
Уровень 1 — Проектное бронирование (WI с клиентом): всегда разрешено если слот свободен
Уровень 2 — Личные встречи (без клиента): руководитель может отключить этот тип
→ «Знаменка только для проектов» — частные встречи пересылаются в переговорную
```
(V2, не в первом релизе)

### Уведомления при бронировании студии

```
Знаменка чёрная / Телестудия  →  уведомление: ТВ отдел + Технический отдел ТВ
Радиостудия / Романов         →  уведомление: Радио редакция
Нижняя студия / Аудиостудия   →  уведомление: Аудио департамент
Знаменка камин (митап)        →  без производственного отдела
```

### Кто может бронировать студию

```
Продюсер             → в рамках WI клиентского или внутреннего проекта (авто-апрув)
Руководитель отдела  → для нужд своего отдела (авто-апрув)
Любой сотрудник      → только переговорная / камин (без производственной студии)
Руководитель ТВ      → заблокировать / разблокировать любую студию
```

## ✅ Внепроектные задачи — зафиксировано

Три источника задач в системе:

```
ИСТОЧНИК 1 — Из проекта (Work Item → отдел → сотрудник)
  Продюсер создал проект → подключил ТВ-отдел →
  руководитель назначил Иванова → Иванов видит задачу

ИСТОЧНИК 2 — Отдельная задача отдела (без проекта)
  Технический отдел: «Формирование выездного комплекта»
  ТВ-команда: «Подготовка шаблонов заставок»
  Бухгалтерия: «Закрытие квартала»
  → Ставится руководителем отдела на своих людей

ИСТОЧНИК 3 — Кросс-командная встреча или задача (ограниченно)
  Юзер     → может назначить встречу в календарь любому (Zoom / офлайн)
  Рук-ль   → может поставить задачу только в рамках своего отдела
  Прод/Дир → может поставить задачу ЛЮБОМУ в компании
  
  «Иванов, подготовь справку к пятнице» — ставит только Прод/Дир
  → Прилетает в личный кабинет Иванова
  
  Юзер хочет попросить коллегу из другого отдела → только через «Встречу в календарь»
```

Долгосрочные задачи отдела (годовые → квартальные):
- Создаются как задачи с длинным дедлайном, разбиваются на подзадачи
- Отображаются в виде Гантта на уровне отдела
- Не привязаны к клиентскому проекту

## ✅ Универсальный инстанс задачи

Одинаковая структура везде — независимо от источника:

```
Задача
  ├── Название / Описание
  ├── Кто поставил + когда
  ├── Кому назначена
  ├── Статус: Новая → В работе → Закрыта
  ├── Дедлайн (дата, не время — слишком детально)
  ├── Приоритет (горящая / обычная / низкий)
  ├── Вложение / ТЗ (ссылка на Google Sheet, файл, и т.д.)
  └── Чат/комментарии (хронология обсуждения)
```

**Типы задач:**
```
Системные (для всей компании):
  • Zoom-встреча
  • Встреча офлайн
```

## ✅ Нагрузка сотрудников — параметр

Сложный учёт часов не нужен. Нужен простой параметр.

**Предлагаемое решение: два типа нагрузки**

```
ТИП 1 — Событийная нагрузка (конкретная дата и время)
  Work Items с датой: ТВ-эфир, Съёмка, Оффлайн, Радио
  → Человек занят полностью в эту дату/время
  → Конфликт определяется точно по времени

ТИП 2 — Фоновая нагрузка (дедлайн, без фиксированного времени)
  Work Items с дедлайном: Монтаж, Моушн, Постпродакшн, Дизайн
  → Человек "имеет текущий проект" до дедлайна
  → Не блокирует конкретный день, но учитывается в нагрузке
```

**Метрика нагрузки на сотрудника за неделю/месяц:**

```
Событийная:  количество занятых дней (дат с Work Items)
Фоновая:     количество активных фоновых Work Items
Итог:        занятых_дней + (активных_фоновых × 0.5)  ← коэффициент можно настроить
```

Пример:
```
Иванов, апрель:
  Событийные: 3 съёмки + 2 эфира = 5 занятых дней
  Фоновые: 1 монтажный проект = +0.5
  Нагрузка: 5.5 из ~22 рабочих дней → 25%
```

Это даёт **понятный и честный показатель** без ручного учёта времени.

## ✅ Учёт времени — финальная позиция

**Ручной ввод времени — отклонён.** Причины:
- Человек не помнит точно
- Параллельные задачи невозможно разделить
- Никто не будет заполнять добросовестно

**Принятый подход: автоматические временны́е метки**

```
Задача создана      → timestamp
Взята в работу      → timestamp  ← начало
Закрыта             → timestamp  ← конец

«Время на задачу» = закрыта − взята в работу
```

**Честное ограничение:** если задачу взяли в понедельник, занимались параллельными делами, закрыли в четверг — засчитается 4 дня. Это неточно. **Принимаем это как допущение** — метрика показывает «задача жила X дней», а не «X дней чистого труда».

**Что реально можно измерять:**

```
МЕТРИКА                          ЧТО ПОКАЗЫВАЕТ
───────────────────────────────  ────────────────────────────────────
Задач закрыто за период          Продуктивность / скорость
Активных задач сейчас            Текущая нагрузка
Просроченных задач               Проблемы с планированием
% закрытых в дедлайн             Дисциплина / реалистичность оценок
Средняя «жизнь» задачи по типу   Поможет лучше ставить дедлайны
Занятых событийных дней          Физическая занятость (съёмки/эфиры)
```

Вместе — честная картина без иллюзии точного тайм-трекинга.

## Итерация 1 — Учёт времени (отдельный вопрос)

### Почему ручной ввод не работает

- Не знаешь точно сколько потратил (ретроспективно всегда неточно)
- Параллельные задачи невозможно разделить
- Рабочий день имеет переменную длину
- Нет стимула заполнять — данные будут неполными

### Альтернативные подходы

**Вариант A — Смены как единица учёта**
```
Сотрудник назначен на смену (4 часа) под задачу X
→ 4 часа автоматически засчитываются задаче X
Плюс: уже есть ShiftPlanner, интеграция минимальна
Минус: не учитывает параллельные задачи внутри смены
```

**Вариант B — Оценка задачи + факт выполнения**
```
Руководитель ставит задачу с оценкой (story points или часы)
Сотрудник помечает Done
→ Аналитика: план vs факт по оценкам, не по реальному времени
Плюс: нет ручного ввода времени
Минус: точность зависит от качества оценок
```

**Вариант C — Ежедневный чекин (Daily Log)**
```
Раз в день (или при закрытии задачи) сотрудник отмечает прогресс в %
→ Система сама считает израсходованное от плановых часов
Плюс: меньше трения чем ввод точного времени
Минус: всё ещё субъективно
```

**Вариант D — Только смены, без задачного учёта**
```
Не считаем время на задачи вообще
Считаем: сколько смен / рабочих дней потратил отдел на проект
→ Финансовая аналитика через ставки за смену
Плюс: самый простой, данные уже есть
Минус: нет детализации по конкретным работам
```

## ✅ Ответы на сценарии — зафиксированные решения

**А — Отдел не может отказать**
Руководитель либо даёт штатного исполнителя, либо фрилансера на эту позицию.
Концепции «отказа» нет — есть только назначение (кем угодно из доступных людей).

**Б — Статус «Сдан» и заморозка**
```
Проект «Сдан» = аккаунт-менеджер получил финальный ОК от заказчика
  УСЛОВИЕ: ВСЕ задачи внутри всех WI проекта, закрыты
  (задачи отделов, кросс-командные; независимо от того, на какой стадии WI были созданы)
  Система блокирует кнопку «Сдан» если есть хотя бы одна открытая задача.
  
  → Проект замораживается: редактировать нельзя НИЧЕГО
  → ИСКЛЮЧЕНИЕ: Финотдел может переключить финансовый флаг (Ожидает → Оплачен)
  → Экстренная разморозка — закрытая функция (только Прод/Дир или Админ)
  → Добавить WI в замороженный проект = экстренная функция
```

**Г — Копирование и шаблоны**
```
Любой Work Item → кнопка «Копировать»
Продюсер может сохранить Work Item как шаблон (дополнительная функция)
Пример: шаблон «Трансляция с Моушн и Звуком» = преднастроенный набор
```

**Д — Дедлайн отдела внутри Work Item**
```
Продюсер подключает отдел → сразу задаёт дедлайн для этого отдела
  (может отличаться от даты Work Item: эфир 15 апр, Моушн должен сдать 12 апр)

Руководитель отдела может сдвинуть дедлайн
  → Продюсер получает уведомление об изменении дедлайна
```

**Зависимости между Work Items (вопрос В)**
Под «зависимостью» имелось в виду: «Монтаж не может начаться пока не завершена Съёмка».
→ На первом этапе формальных блокировок нет. Монтажёр видит статус Work Item «Съёмка»
и сам понимает когда материал готов. Флаг «ожидает» — V2.

## ✅ Финальная модель статусов проекта

**Модель статусов проекта (независима от WI-статусов):**

```
ЗАЯВКА          Пресейл, бриф получен, непонятно будет ли проект
  │             WI уже можно создавать (они будут в статусе «Заявка»)
  │             авто-переход → когда хотя бы один WI переходит в «Реализацию»
  ▼
РЕАЛИЗАЦИЯ      Продан, договорились, производство идёт
  │             WI и отделы активно работают
  ▼
СДАН            АМ получил ОК от заказчика → Проект замораживается
                (ручной: АМ нажимает; условие: все WI = «Сдан»)
```

**Финансовый флаг проекта (отдельная ось, не статус):**
```
Ожидает оплату  →  Оплачен   (Финотдел меняет когда деньги пришли)
```
«Сдан» = физическая сдача; «Оплачен» = финансовая финализация. Оба нужны.

**Статусы проекта и WI — независимы:**
Проект авто переходит в «Реализацию» когда первый WI переведён в «Реализацию».
Остальные WI этого проекта могут оставаться в «Заявке».

**Плюс отдельные выходные статусы из любого состояния:**
```
ОТМЕНЁН    — клиент отказался или внутреннее решение
НЕ СОГЛАСОВАН — дошли до переговоров, не продали
```

**Финансовый флаг (отдельно от основного статуса):**
```
Ожидает оплату  →  Оплачен
```
Отдел (спецотдел / бухгалтерия) переключает флаг когда деньги пришли.
«Сдан» = АМ получил ОК от клиента → заморозка. Флаг «Оплачен» отдельно (решение #1).

**Почему НЕ разделяем «Сдан физически» и «Сдан финансово» в основной статус:**
Добавляет лишний переход. Финансовый флаг решает задачу проще —
видно и что команда закончила, и что деньги пришли.

## ✅ Модель ролей — финальная (упрощённая для V1)

### Два измерения

**Системная роль** — глобальные права в системе (4 уровня).
**Контекстная роль** — кем человек является в конкретном Work Item (ассистент режиссёра, куратор выезда и т.д.). Поле для справки, на права не влияет.

---

### 4 системных роли

```
УРОВЕНЬ          РОЛЬ                    КТО
───────────────  ──────────────────────  ──────────────────────────────────────

2                Руководитель            Руководители отделов внутри департаментов
3                Продюсер / Директор     Продюсеры ТВ-дептамента +

                                         (одинаковые права, одна роль в V1)

```

**Фрилансер** — отдельный тип аккаунта (не роль в основной системе). Только внешний портал.

**Аккаунт-менеджер** — функция, не роль. Продюсер/Директор, ведущий клиентскую коммуникацию по проекту. Ставит финальный статус «Сдан».

```
  └─ Сотрудники        ← роль Юзер
  (└─ Руководитель отдела  ← роль Руководитель, если назначен отдельно)
```

```
Видеть финансы проекта                  ❌      ✅       ✅        ✅

ФРИЛАНСЕРЫ И ОПЛАТА
Видеть запросы на оплату                ❌      ✅       ✅        ✅
Подтвердить оплату фрилансеру           ❌      ❌     фин.отд    ✅
Изменить финансовый флаг проекта        ❌      ❌     фин.отд    ✅
  (Ожидает оплаты → Оплачен)

СИСТЕМА
Создавать / редактировать пользоватей   ❌      ❌       ❌        ✅
Управлять справочниками (отделы и т.д.) ❌      ❌       ❌        ✅
```

**Принцип «широкого просмотра» в V1:**
Смотреть может почти каждый — изменять только в своей зоне ответственности.
Ограничения по просмотру (например скрыть финансы от юзеров) можно добавить в V2.

**Внутри проекта руководитель видит:**
- Полную карточку проекта (все Work Items, все отделы)
- Но может изменять ТОЛЬКО данные своего отдела (задачи, исполнители, дедлайн отдела)

## ✅ Два режима работы в компании — зафиксировано

Фундаментальное различие которое влияет на всю модель:

```
РЕЖИМ              КТО                       КАК РАБОТАЕТ
─────────────────  ────────────────────────  ──────────────────────────────────────
Проектный          ТВ департамент            Есть проект → есть работа
                   Дизайн · Моушн            Каждый проект = набор Work Items
                   Постпродакшн              Учёт: задачи привязаны к WI
                   Бренд медиа · Корп медиа

Потоковый          Радио департамент         Работа идёт по годовому контракту
                                             Один Проект-«зонтик» на год
                                             Рутина = план-отчёт (задачи отдела)
                                             Уникальные события = отдельные WI

Внутренний         Финансовый · Персонал     Работают независимо от клиентских
                   Администрация             проектов. Только канбан + задачи отдела
```

## ✅ План-отчёт = задачная система глазами сотрудника

Уточнение: план-отчёт — это **не отдельный инструмент**, это то же самое задачное представление.

```
«Что мне делать сегодня» = мои активные задачи (из всех источников):
  ├── Задачи от руководителя в рамках проекта
  ├── Задачи которые я сам поставил себе (в проекте или свободные)
  └── Задачи от коллег (кросс-командные)

«Что я сделал» = задачи закрытые сегодня (timestamp закрытия)
```

Отдельной формы заполнения нет — система задач И ЕСТЬ план-отчёт.

**Шаблоны типов задач** (чтобы быстро создавать повторяющиеся):
```
Системные (у всех):     Zoom-созвон · Офлайн встреча · Задача
Личные:                 каждый сотрудник создаёт свои шаблоны
Департаментские:        Монтаж · Радиоэфир · Дизайн-правки · и т.д.
                        (общие для всего отдела, создаёт руководитель)
```

Задача всегда может быть привязана к проекту/клиенту — это даёт аналитику затраченного времени по проектам.

---

## ✅ Радио: потоковый проект — решение

```
Абонементный проект («Радиошоу на год»)  ← ТОЛЬКО для Радио-департамента
  ├── Тип: Проект-«зонтик» (нет обязательных Work Items)
  ├── Привязан к клиенту и годовому договору
  ├── Сотрудники Радио-отдела ссылаются на него в план-отчётах
  ├── АМ назначается (обязательно, как у обычного проекта)
  └── Work Items опционально — только если есть уникальное событие
      (например, выездной эфир или спецвыпуск)
```

**Ключевые отличия зонтика от обычного проекта:**
```
Создать зонтик    → только Радио-департамент (роль Прод/Дир в Радио-депт)
Закрыть (Сдан)   → только после завершения контрактного периода (вручную АМ)
Статус в году    → весь период = «Реализация», WI внутри закрываются независимо
АМ               → обязателен, как и у обычного проекта
```

Один Проект-«зонтик» на год. Рутина фиксируется через план-отчёт.
Уникальные события — отдельные Work Items внутри этого же Проекта.

## 🧪 Сценарии для проверки системы

Каждый сценарий проверяет конкретный механизм. Ожидаемый результат указан — если он не выполняется, там дыра.

---

### Сц-1 — Полный цикл проекта

```
1. Продюсер создаёт «Юбилей Газпром» + WI «Трансляция 20 мая, Знаменка» — статус WI: Заявка
   Знаменка заблокирована с пометкой «Предварительно» в календаре
   Подключены: ТВ-отдел (дедлайн 19 мая), Моушн (17 мая), Звук (15 мая)
   Продюсер добавляет задачи каждому отделу — отделы их НЕ видят (ещё Заявка)
2. После встреч с заказчиком: продюсер переводит WI в «Реализацию»
   → Все задачи публикуются: ТВ, Моушн, Звук видят свои задачи одновременно
   → Знаменка: бронь переходит в «Подтверждено» (стандартный вид)
   → Проект «Юбилей Газпром» авто переходит в «Реализацию»
3. Если дедлайн не задан при подключении → автоматически = дата WI (20 мая)
4. Руководитель ТВ решает взять фрилансера Васю
   → запрос уходит продюсеру → продюсер подтверждает → Вася добавлен
   → конфликт-чек: Вася не занят в другом WI 20 мая
5. Все отделы → «Завершено» → WI автоматически = «Сдан»
6. АМ (роль: Продюсер/Директор) ставит проект «Сдан» → заморозка
   Финансовый флаг = «Ожидает оплаты» (не «Оплачен» — деньги ещё не пришли)
7. Деньги пришли → Финотдел меняет флаг на «Оплачен» (единственное поле в замороженном проекте)
```

**Ожидаем:** каскад статусов работает, заморозка не мешает Финотделу, уведомления на каждом шаге уходят нужным людям.

---

### Сц-2 — Телерадио: один WI, два обязательных отдела

```
1. Продюсер создаёт WI «Телерадио-концерт, 15 апр»
   Формат: Телерадио
   → система требует подключить ТВ-отдел И Радио-редакцию (нельзя только один)
   → попытка подключить только ТВ-отдел → ошибка / предупреждение

2. Знаменка (ТВ) и Романов (Радио) блокируются автоматически → 15 апр
   Моушн и Дизайн подключены вручную для заставок

3. ТВ-отдел завершает свою часть → статус ТВ = «Завершён»
   Радио ещё работает → WI остаётся «В работе» (не все отделы завершены)

4. Радио завершает → все отделы = «Завершён» → WI автоматически = «Сдан»
   → АМ может ставить проект «Сдан»
```

**Ожидаем:** система не даёт создать WI формата «Телерадио» без обоих отделов; статус WI ждёт завершения всех подключённых отделов; студии блокируются каждая под свой отдел.

### Сц-16 — Два фрилансера с одинаковым именем

### Сц-18 — Заблокированная студия

```
1. Оборудование в Знаменке чёрной на ремонте — руководитель ТВ блокирует студию
```

## ❓ В-35 — Копия WI: в каком статусе создаётся?

**Ситуация:**
При копировании WI (Сц-3, серийный проект) — продюсер получает копию.
В новой модели WI всегда начинает в «Заявке». Но копия уже содержит детальные задачи.

```
Вопрос:
  → Копия создаётся в «Заявке» (нужна повторная публикация, даты проставить и нажать)?
  → Или копия сразу в «Реализации» (задачи видны отделам, не нужна публикация)?
  → Для Сц-3 (10 эпизодов): продюсер хочет скопировать быстро, поменять только даты
    и сразу опубликовать — какой сценарий удобнее?
```
