# TV Shifts — Масштаб, роли и интеграции

Документ описывает целевую архитектуру системы с точки зрения пользователей, ролей и внешних интеграций. Обновляется по мере уточнения требований.

---

## Целевой масштаб

| Параметр | Значение |
|----------|----------|
| Всего пользователей | ~60 |
| Одновременно активных | ~15 |
| Количество ролей | 10–15 |

## Модель разрешений (целевая архитектура RBAC)

Вместо enum `Role` (3 значения) — таблица разрешений. Добавление роли = INSERT, не миграция.

### Таблицы (целевая схема)

```sql
-- Роли
roles (id UUID, name TEXT UNIQUE, description TEXT)

-- Связь пользователь → роль(и)
user_roles (userId UUID → users, roleId UUID → roles, UNIQUE(userId, roleId))

-- Список разрешений
permissions (id UUID, name TEXT UNIQUE, description TEXT)
-- Примеры: 'projects:read', 'projects:write', 'sync:trigger',
--           'members:manage', 'kanban:write', 'analytics:read',
--           'users:manage', 'db:manage', 'bitrix:send'

-- Связь роль → разрешения
role_permissions (roleId UUID → roles, permission TEXT → permissions, UNIQUE(roleId, permission))
```

## Персональный контекст пользователя

Каждый пользователь работает в своём контексте:
- **Профиль** — должность, тип занятости, ставка, контакты
- **Мои проекты** — проекты, где пользователь в команде
- **Мои задачи** — открытые задачи в Kanban / список дел
- **Упоминания** — уведомление при добавлении в отдел или задачу
- **Свод дел продюсера** — агрегированный список всего незакрытого по всем проектам

## Интеграция Битрикс24

**Цель:** отправка вызывного листа, статуса смены, уведомлений.

**Подход:**
1. OAuth-приложение в Битрикс24 (или webhook для простого PoC)
2. Асинхронная очередь (`pg-boss`) — не блокировать основной запрос
3. Модуль `apps/api/src/integrations/bitrix/`

**Поток данных:**
```
Продюсер утверждает смену
  → POST /sync/bitrix/:projectId
  → задача в очереди
  → воркер: читает проект + команду → формирует payload → отправляет в Битрикс API
  → запись результата в audit_events
```

**Статус:** PoC не начат. Нужно: изучить Bitrix24 REST API, выбрать тип приложения.

## Интеграция с сервером техники

**Описание:** отдельный проект (~1000 позиций техники). Двусторонняя интеграция.

### Исходящий поток (TV Shifts → Equipment server)

| Событие | Действие |
|---------|----------|
| Создан проект с отделом (тип: застройка/монтаж) | Запрос доступной техники на дату |
| Подтверждён отдел | Резервирование техники под проект |
| Экспорт проектов | Передача всего списка проектов для отображения на equipment-сервере |

### Входящий поток (Equipment server → TV Shifts)

| Событие | Действие |
|---------|----------|
| Изменение статуса техники | Уведомление в TV Shifts (если техника зарезервирована) |
| Загрузка людей | Проверка занятости сотрудника сразу в обоих системах |

### Архитектура

```
TV Shifts API
  └── apps/api/src/integrations/equipment/
        ├── client.ts     — HTTP-клиент к equipment-серверу
        ├── jobs.ts       — задачи в pg-boss очереди
        └── sync.ts       — двусторонняя синхронизация проектов
```

**Статус:** архитектура определена, реализация не начата. Приоритет — после ролевой системы.

## Уведомления и упоминания (целевая схема)

```
Текущая Notification:
  id, userId, type, message, isRead, createdAt

Дополнить (миграция):
  mentionedUserId — кого упомянули
  sourceType      — 'task' | 'kanban' | 'note' | 'project'
  sourceId        — UUID источника
  authorId        — кто создал упоминание
```

**Сценарии:**
- Продюсер добавляет участника в отдел → `specialist` получает уведомление «Вас добавили в [проект], [отдел]»
- Назначение задачи в Kanban → `assignee` получает уведомление с ссылкой на карточку
- У продюсера: агрегированный вид «Мои дела» — все задачи по всем проектам со статусами

## Нагрузочные характеристики и инфраструктура

| Аспект | Текущее | Целевое |
|--------|---------|---------|
| Concurrent users | — | 15 |
| Auth | JWT httpOnly cookies | Без изменений (stateless, масштабируется) |
| DB connections | Prisma pool (default 10) | + pgBouncer при росте нагрузки |
| API instances | 1 | Готово к горизонтальному масштабированию (stateless) |
| Caching | TanStack Query (client) | + Redis (при необходимости кэша на сервере) |
| Queue | нет | pg-boss поверх PostgreSQL |
| Monitoring | нет | Grafana + Loki + Prometheus (см. [09-observability.md](09-observability.md)) |
