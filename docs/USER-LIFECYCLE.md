# Жизненный цикл пользователя

> Статус: **Этап 1 реализован и задеплоен** (2026-06-10): `POST /users/:id/deactivate` / `/reactivate`,
> тоггл «Работает сейчас» в карточке, автоген табельных, показ уволенных. Этап 2 (API с inventory) — впереди.
> Связано: `docs/INTEGRATION.md` (SSO, общий `public.users`).

## Принципы
- Сотрудники заводятся **только через Nexus** (единая точка регистрации).
- **Аккаунты не удаляем** — переводим в неактивный статус (архив). Удаление осиротило бы связи (задачи, проекты, треки, роли в WorkItem).
- Доступ к приложению и права **внутри** него изолированы: Nexus решает «есть ли доступ» (вкл/выкл), а роли/permission внутри inventory выдаёт его админ. Логи «что брал / когда» и условия освобождения — на стороне inventory.
- Штат и фрилансеры — **один и тот же цикл**; различаются форматом табельного (форматы уже заданы в БД).

---

## 1. Регистрация (создание)
1. **Профиль** — `nexus.users` (ФИО, табельный, должность, отдел), логина ещё нет. Источники:
   - **«+ Добавить сотрудника/фрилансера»** — основной способ;
   - **Импорт из Google Sheets** — ⚠️ **рудимент** (разовая первичная загрузка). В дальнейшем функционал отключим; новых заводим вручную.
2. **Выдача доступа** — «Выдать доступ» / «Выдать доступ всем»:
   - создаётся `auth.users` (**временный пароль**) + `public.users` (id = auth.uid) + связка `nexus.users.auth_id`;
   - если email уже в `auth.users` — **привязка существующего** (пароль не меняем).
3. **Первый вход** — Nexus требует **сменить временный пароль**.
4. **Доступ в inventory** — по флагу `canAccessInventory` в Nexus; роли/permission внутри inventory — его сторона.

## 2. Статусы
| Статус | Вход | Назначать задачи/встречи | Данные/история | Табельный |
|--------|------|--------------------------|----------------|-----------|
| **Активный** | да | да | — | есть |
| **Неактивный (уволен/архив)** | **нет (бан)** | нет | **сохраняются** | снят |

**«Уволен» и «архив» — один и тот же статус** (неактивный): живой аккаунт без возможности входа, все данные и связи целы (видны прошлые задачи/проекты/треки, доступны для сортировки/отчётности).

---

## 3. Увольнение / восстановление

### Этап 1 — сейчас (без inventory)
Увольнение = **блокировка доступа**, обратимо. Inventory **не спрашиваем**.
```
Уволить:
  • снять табельный (tabNumber = null)
  • забанить auth.users (GoTrue ban) + отозвать сессии  → вход невозможен нигде
  • nexus.users: isActive = false, status = 'archived'
  • public.users.is_active = false
  → сотрудник неактивен (нельзя назначать новое), но существует; история цела

Восстановить:
  • снять бан auth.users
  • nexus.users: isActive = true, status = 'active' (+ вернуть табельный при необходимости)
  • public.users.is_active = true
  → снова может войти
```
При попытке входа уволенного — страница «доступа нет» (бан в `auth.users`).

> Это закрывает текущую дыру: сейчас «Удалить регистрацию» гасит только `nexus.users.isActive`, и уволенный всё ещё может войти в inventory. После Этапа 1 бан `auth.users` блокирует вход во **все** приложения.

### Этап 2 — позже (через inventory)
Перед увольнением Nexus **спрашивает inventory** по API: «можно ли освободить сотрудника?»
- inventory реализует **условия освобождения** (незданное оборудование и т.п.) и **ручной аппрув своего админа**;
- логи «что брал / когда» остаются на стороне inventory;
- только после «OK» от inventory Nexus увольняет.
- Контракт API общения Nexus ↔ inventory — спроектировать на Этапе 2.

---

## 4. Удаление (НЕ практикуем)
Физическое удаление аккаунтов не используем (рвёт связи). Только для мусорных/тестовых. Вместо — неактивный статус (архив).

---

## Что блокирует увольнение
Пока — **ничего** (Этап 1: всегда можно уволить/восстановить). Перечень блокирующих условий (оборудование, незакрытые задачи, активные проекты) — определим позже (Этап 2, на стороне inventory и/или Nexus).

## План реализации
- **Этап 1 — ✅ реализован (2026-06-10):** тоггл «Работает сейчас» в карточке (штат и фрилансеры) + бэкенд `POST /users/:id/deactivate|reactivate`: бан/анбан `auth.users` (GoTrue `ban_duration`) + `nexus.users.isActive/status` + `public.users.is_active` + снятие табельного. Для штата и фрилансеров одинаково. Админ-аккаунты через UI не увольняются (read-only карточка).
  - Нюанс: бан не отзывает уже выданные access-токены — окно «уволенный ещё в inventory» ≤ TTL токена (~1ч); Nexus блокирует мгновенно (проверка `isActive` на каждом запросе). Мгновенный отзыв сессий — в TODO (пожелание).
- **Этап 2:** API Nexus ↔ inventory (запрос на увольнение + аппрув), условия блокировки. Контракт — в `megapolis-platform/api/`.
