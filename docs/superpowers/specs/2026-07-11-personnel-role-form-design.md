# Дизайн: форма роли/должности сотрудника в «Персонале»

> Статус: на ревью Влада. Дата: 2026-07-11. Ветка: knyazzer.
> Брейншторм-решения согласованы (A/B/C + «руководитель = член отдела: да»).

## 1. Проблема

Сейчас карточка сотрудника (`PersonnelPage.tsx`, EditPanel) правит **плоские свободнотекстовые поля**
`User.position` / `User.department` / `User.subDept` — они только для отображения и **не связаны** с
реальной оргструктурой (`UserDivision` / `Division.headId` / `Department.directorId`), которая драйвит RBAC.
Итог: должность вводится как попало, роль (руководитель/директор) назначается отдельно в «Структуре»,
данные рассинхронены.

## 2. Цель

Свести назначение роли и места в оргструктуре в карточку сотрудника через каскад выпадающих списков.
Форма пишет **реальные связи оргструктуры** (то, что использует RBAC), а не свободный текст.

**Не-цель (out of scope):** редактор самой структуры (создание департаментов/отделов) — остаётся в
«Структуре»/OrgChart. Здесь только назначение сотрудника на существующие узлы.

## 3. Модель формы (каскад)

Порядок полей (каждое следующее зависит от предыдущего):

1. **Тип должности** — `Сотрудник` / `Руководитель` / `Директор` (обязательно)
2. **Департамент** — селект из существующих (обязательно для всех типов)
3. **Отдел** — селект отделов выбранного департамента.
   Показывается для `Сотрудник` и `Руководитель`; **скрыт для `Директор`** (у директора отдела нет).
4. **Уточнение** — свободный текст (напр. «Монтажёр», «Дизайнер»). **Только для `Сотрудник`**
   (у руководителя/директора роль ясна из типа).

**Совмещение:** штатно одно назначение. Кнопка «+ Добавить должность» даёт **второе** назначение
(тот же каскад). Максимум — 2. При двух должностях доступ RBAC = **объединение** модулей, уровень
считается отдельно в каждом департаменте (уже так работает в `services/access.ts`).

## 4. Семантика записи (тип → связи БД)

Форма отправляет **желаемый набор назначений**, сервер реконсилит связи под него (декларативно).

| Тип | Пишем |
|---|---|
| **Сотрудник** (member) | `UserDivision(userId, divId, position = уточнение)` |
| **Руководитель** (head) | `Division.headId = userId` **и** `UserDivision(userId, divId, position = 'Руководитель отдела')` (решение C: head — ещё и член отдела, иначе висит вне списков/свода) |
| **Директор** (director) | `Department.directorId = userId` (без `UserDivision` — у директора нет отдела) |

**Денормализация (решение A):** после реконсиляции сервер синхронит плоские поля `User.department` /
`User.subDept` / `User.position` из первого (основного) назначения — чтобы таблица «Персонала»
(читает плоские поля) показывала актуальное без переписывания. Кэш, источник правды — связи.

## 5. API-контракт

Новый эндпоинт (логика оркестрации — на сервере, не на фронте; урок BAC):

```
PUT /users/:id/assignments
Гард: admin ∨ hr.orgstructure:edit (как структура; сейчас structure.ts — adminOnly, начинаем с admin)
Body (Zod .safeParse):
{
  assignments: Array<{                      // 1..2 элемента
    type: 'member' | 'head' | 'director',
    deptId: string,
    divId?: string,                         // обязателен для member/head, запрещён для director
    specialization?: string,                // только для member
  }>,
  replace?: boolean                          // подтверждение замены занятого слота head/director
}
```

**Поведение (в транзакции):**
1. Валидация: для `director` — `divId` отсутствует; для `member`/`head` — `divId` принадлежит `deptId`.
2. **Конфликт слота** (решение B): если `head`-назначение на отдел, где `headId` уже занят другим
   пользователем (или `director` на департамент с чужим `directorId`) и `replace !== true` →
   **409** `{ error: 'slot_taken', slot: 'head'|'director', currentUserId, currentUserName, deptOrDivName }`.
   Фронт показывает подтверждение «у отдела уже руководитель X — заменить?»; повтор с `replace: true`.
   При `replace: true` — старого head/director **сдвигаем в рядовые** (снимаем `headId`/`directorId`;
   его `UserDivision`-членство остаётся — он просто перестаёт быть руководителем).
3. **Реконсиляция** связей пользователя `:id` под новый набор:
   - `UserDivision`: привести к набору member/head-назначений (добавить недостающие, удалить лишние,
     обновить `position`).
   - `Division.headId`: выставить там, где тип head; снять там, где пользователь был head, но в новом
     наборе этого нет.
   - `Department.directorId`: аналогично для director.
4. Синк плоских полей `User.department/subDept/position` из основного (первого) назначения.
5. Ответ `200` — обновлённая карточка (как `GET /users/:id`).

Существующие примитивы `structure.ts` (`PATCH /divisions/:id {headId}`, `POST /memberships` и т.д.)
переиспользуются как helpers внутри, но фронт их напрямую для этой формы **не дёргает** —
только консолидированный эндпоинт (атомарность + одна точка валидации/гардов).

## 6. UI

`PersonnelPage.tsx` EditPanel: секцию свободных `position`/`department`/`subDept` **заменить** на каскад.

- Строка назначения: `[Тип ▼] [Департамент ▼] [Отдел ▼ | —] [Уточнение ____]`
  - `Отдел` дизейблится/прячется при типе `Директор`.
  - `Уточнение` видно только при типе `Сотрудник`.
  - Отдел-селект фильтруется по выбранному департаменту (данные из `GET /structure`).
- «+ Добавить должность» → вторая строка назначения (та же логика). Кнопка исчезает при 2 строках.
  «✕» убирает вторую строку.
- Сохранение: `PUT /users/:id/assignments` с массивом. На `409 slot_taken` — модалка подтверждения
  (по железному правилу попапов: закрытие только mousedown+mouseup на оверлее), «Заменить» → повтор с `replace:true`.
- Имя/почта/табельный сохраняются как раньше (`PATCH /users/:id`), отдельно от назначений.

Таблица «Персонала» не меняется (читает плоские поля, которые сервер синкает).

## 7. Краевые случаи

- **Смена типа существующего сотрудника** (member→head): реконсиляция выставит `headId`, членство
  сохранится/обновится. head→member: снять `headId`, членство остаётся.
- **Пустой отдел без руководителя** — обычный кейс назначения head (слот свободен, без 409).
- **Один человек — два департамента** (совмещение): две строки, разные `deptId`. Реконсиляция ведёт
  все связи разом. Уровни считаются отдельно (уже так в `access.ts`).
- **Директор + член другого отдела**: `director` в одном департаменте + `member` в другом — валидно
  (2 назначения). Первое (основное) определяет плоские поля.
- **Удаление всех назначений** — форма позволяет? В v1: минимум одно назначение обязательно (нельзя
  сохранить пустой набор). Снятие сотрудника со всех ролей — через увольнение/деактивацию (отдельно).

## 8. Тесты (`users.test.ts` или новый `assignments.test.ts`)

- member: создаёт `UserDivision` + синкает плоские поля.
- head: ставит `Division.headId` + создаёт членство (решение C).
- director: ставит `Department.directorId`, `UserDivision` не создаёт; `divId` в body → 400.
- занятый head-слот без `replace` → 409 `slot_taken`; с `replace:true` → старый head теряет `headId`.
- смена head→member снимает `headId`.
- совмещение: 2 назначения → обе связи; удаление одного из набора снимает соответствующую связь.
- гард: не-admin без `hr.orgstructure` → 403.

## 9. Порядок реализации

1. Backend: эндпоинт `PUT /users/:id/assignments` + Zod + транзакция реконсиляции + helper денормализации.
2. Тесты бэка (п.8) — зелёные.
3. Frontend: каскад в EditPanel + фильтрация отделов + вторая строка + модалка замены.
4. Ручная проверка в браузере (dev-стенд): назначить сотрудника/руководителя/директора, совмещение,
   замену слота; сверить таблицу и RBAC (войти под назначенным head → появился Свод отдела).
