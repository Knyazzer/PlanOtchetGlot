# Календарь Nexus — решения по механикам (со слов Влада, «допрос» 2026-08-02)

> Зафиксированные ответы Влада на вопросы по календарю/задачам/трекам/чатам. Это **решения-фундамент**, каждый крупный блок → свой спек/план перед реализацией. Многие пункты меняют модель данных (Prisma) и требуют бэкенда. Опирается на роадмап `2026-08-02-calendar-and-visual-roadmap.md`.

## 1. Что показывается в календаре (сущности)

- **Время-блоки в дне/неделе = `Event`** (встречи и пр.), внутри дня, со временем.
- **Канбан-`Task`** попадает в сетку времени **опционально** — только если сотрудник указал время «со скольки до скольки» он ей занимается. По умолчанию задача в сетке не рисуется.
- **События обязательно попадают в план-отчёт сотрудника.**
- У сотрудника формируется **несколько групп** элементов дня: свои задачи, задачи от руководителя, встречи/события (в т.ч. квартальные), назначенные ему — их много. Все они видны в его дне.
- В **месяце** отображается ВСЁ: HR-статусы, задачи (со временем), встречи.

## 2. «Весь день» и многодневность — только HR-слой

- **Обычный `Event` — всегда однодневный, со временем. All-day ему НЕ нужен.**
- «Весь день» и многодневность — **только HR-статусы** (`CalendarEntry`): отпуск, больничный, удалёнка(?), отгул, **командировка**. Всё остальное (встречи/мероприятия) — внутри дня.
- All-day/многодневное рисуется **полосой сверху колонки дня** (как Google Calendar), НЕ вертикальным блоком на всю высоту, НЕ отдельным столбцом.
- Многодневное = **одна запись `дата ОТ–ДО`** → добавить `endDate` (и, вероятно, признак multi-day) в `CalendarEntry`. НЕ N однодневных экземпляров.

## 3. Статусы сотрудника (частично есть в кабинете)

Уже есть немного функционала: выпадающим списком сотрудник ставит статус. Нужно допроектировать.
- **Базовый статус** — «в работе». Нужно определить полный список статусов (HR-статусы: офис / удалёнка / на проекте / больничный / отпуск / отгул / командировка / «не в рабочее время»…).
- **Авто-скрипт:** 10:00–18:30 автоматически «в работе»; вне рабочего времени — статус «не работаю / закончил работу».
- Из статуса человек может **сам** переключиться на **больничный** → появляется в календаре, все видят.
- Статус = «где человек сейчас»: офис / удалёнка / на проекте (тогда **обязательно подписан проект**, полуавтоматически — если есть проект, привязка ставится сама).
- Выходной / запрос отпуска на день — нужен функционал самозаявки (см. §4).

## 4. Отпуск/больничный — заявка и согласование (новый функционал)

- Сотрудник из **личного кабинета** → «Отправить заявку на отпуск» → заявка **падает руководителю** → руководитель **согласовывает** → сотрудник в отпуске (появляется полосой в календаре).
- **Больничный** — сотрудник может поставить сам (без согласования).
- **Скачивание заявления на отпуск**: форма с полями (сотрудник вводит цифры/даты) → скачать → распечатать → подписать. В шаблоне сразу: на чьё имя, от кого, должность и т.д.

## 5. Параллельные события / overlap (неделя + день)

- **Неделя** (колонка дня-в-неделе): параллельные показываются одновременно, ~**3** макс; следить, чтобы текст НЕ переносился на след. строку, выравнивание адекватное.
- **День** (открытый одиночный день): может поместиться **до ~20** колонок → **динамическая** раскладка по числу параллельных.
- Раскладка — равные колонки, читаемо.
- **Создание параллельного:** зажал-протянул мышкой в **свободной правой зоне** (зазор справа) рядом с существующим → создаётся параллельно. Зазор должен быть визуально нормальным.

## 6. Живой пунктир + карточка сбоку (создание и редактирование)

- **Экран НЕ затемняется.** Остальной календарь **кликабелен** при открытой карточке.
- **Создание:** зажал-протянул → **пунктирная** обводка нового события + **карточка справа** от пунктира (если справа нет места — слева).
- **Двусторонняя связь:** тянешь края пунктира ↔ время в карточке меняется; меняешь время/дату в карточке ↔ пунктир двигается/перебрасывается.
- **Редактирование** (1 клик по событию): открывается карточка сбоку + обводка блока — но **с заливкой** (в отличие от пунктира-создания), чтобы понимать «редактирую», не «создаю». Можно двигать ползунки времени/дату в карточке или тянуть саму обводку.
- **Перетаскивание целиком** (клик-**удержание** по событию): карточка гаснет/затемняется, к мышке привязывается **силуэт** события; тащишь на нужное время/день (сохраняя длительность); **подсвечивается целевой слот** — видно, куда попадёшь (напр. перенос 12–15 → другой день, видно новое время).
- **Клик по другому дню/событию** при открытой карточке → предыдущая карточка закрывается, открывается новая. **Клик в пустоте вне карточек** → все карточки закрываются.

## 7. Иерархия календарей

Итоговый набор (уточнено):
- **Личный сотрудника** — свои задачи/планирование. ДА.
- **Общий компании** — общие встречи/общее. ДА.
- **Проектный** — к проекту прикрепляются люди; при отображении человек видит **только те мероприятия, где он зафиксирован** (не все события компании).
- **HR-статусы** — отпуска/больничные/командировки (полоса сверху).
- **Календарь встреч (мероприятий)** — отдельный; любой может собрать круг людей на встречу. (Отдельного «календаря отдела/департамента» НЕ делаем — департаментский по сути = встречи.)
- **Треки — БЕЗ отдельного календаря.** Встречи по треку указываются как обычные встречи, привязанные к треку (см. §9).

### 7.1. Локации (Знаменки) — БРОНЬ ТОЛЬКО ЧЕРЕЗ ПРОЕКТ (решение + вопрос)
Зоны (Знаменка Каминка/Чёрная/Купол и др.) используются и под проекты, и под встречи; часть требует тех-обеспечения.
- Нужен **календарь локации** (по каждой локации) — видеть, занята/свободна.
- Слот в локации бронируется **только через проект** (внутренний для компании ИЛИ внешний для заказчика): проект даёт бриф, назначенных ответственных, задачи. **Напрямую забивать слот локации нельзя** — иначе нет брифа/непонятно, что нужно.
- Если встрече нужно тех-оснащение локации → **обязателен проект**. Нет проекта → тех-обеспечения нет, можно только «посмотреть день».
- **Следствие:** проекты будут иногда «из одного человека» — это ОК, осознанно.
- **Влад просит второе мнение** (см. §11 Рекомендации).

## 8. Видимость календарей

- Чужие **личные** — не видны.
- **Руководители / директора / гендиректор** — видят календари подчинённых (без переключения). Это часть **агрегации → helicopter-view всей компании** — **параллельная задача/трек**, не блокирует базовый календарь.

## 9. Треки (этап 3 — визуал + новые механики)

- Механики уже есть, нужна **визуальная унификация** под канон.
- Трек = **этапы + задачи внутри этапов**, прогресс отслеживается.
- **Боль:** встречи/события, созданные по треку, **не видны внутри трека** (только в календаре). Хочу видеть **намеченные по треку встречи внутри трека**.
- **Трек = чат (новая механика):** как в канбане (у доски/пула есть чат). При создании нового трека **автоматически создаётся чат** с названием трека; все добавленные люди **автоподключаются**. Можно слать задачи в чат и обсуждать. Из трека создаём задачи/события и обсуждаем в чате.

## 10. Чаты → канон (этап 1)

- Канон = китовый **Messenger**, но канон **эволюционировал**: база ui-kit → support (дореализовано) → **kanban (наиболее полный: меню, мини-аккаунты сотрудников, мобильная адаптивность, реакции/ответы)**. Ориентир — версия из **megapolis-kanban**.
- **Backend в Nexus нужно дореализовать** — Nexus-чат старый, вероятно не все механики kanban/support там есть.
- Сохранить всё, но: 
  - **Чат поддержки** — сделать **сквозным на всю компанию**, НЕ показывать число участников; уведомления из него приходят **только техподдержке**; люди могут зайти и посмотреть решения проблем.
  - **Избранное** (свои сообщения/избранные), **заметки (self)**, **реакции/ответы** (хорошая реализация из kanban — базовые, но рабочие).
- **Realtime:** сейчас Фаза 1. В Nexus **уже есть WebSocket + realtime** (вроде есть «печатает…», авто-приход сообщений) — **проверить**. Redis — пока неясно, нужен ли; если нужен — реализуем, вопрос «когда готовить». Фаза 2/3 — отдельный трек.

## 11. Рекомендации Клода (по открытым местам)

- **§7.1 Локации через проект — согласен**, но чтобы не плодить «проекты из одного человека» с полным весом: предлагаю ввести **лёгкий тип проекта / «бронь-заявку»** — минимальный бриф (что, кто ответственный, нужно ли тех-оснащение), который и бронирует слот локации. Это сохраняет правило «слот только через проект/бриф», но не заставляет заводить полноценный внешний проект под внутреннюю встречу. Обсудить.
- **§3 Статусы** — предложу конкретный список статусов + правила авто-простановки отдельным мини-спеком до реализации.

## 12. Порядок (черновой, декомпозиция)

Крупные независимые треки (каждый — свой спек/план):
1. **Overlap + drag-интерактив календаря** (§5, §6) — фронт, без схемы (Event уже со временем). Самый «визуально-мясной».
2. **Задачи опционально в сетке времени** (§1) — Task со временем в календаре.
3. **HR-статусы + полоса сверху + многодневность** (§2, §3) — схема (`CalendarEntry.endDate`, статусы) + бэкенд + UI.
4. **Заявка на отпуск + согласование + заявление** (§4) — бэкенд-воркфлоу + PDF-форма + кабинет.
5. **Иерархия календарей + проектный/встречи/локации** (§7) — модель календарей + бронь через проект.
6. **Треки: встречи внутри трека + трек-чат** (§9) — интеграция трек↔чат.
7. **Чаты → канон (визуал) + дореализация бэкенда** (§10).
8. **Агрегация helicopter-view для руководителей** (§8) — параллельный трек.
