# Аудит-бриф: механика задач в «Моём кабинете» (Обзор + день)

> Цель: детальный комплексный аудит всей механики задач внутри кабинета сотрудника — с точки зрения одного пользователя (свои задачи), других пользователей (их задачи и отправка задач мне/друг другу), корректного отображения, и **защиты от дурака** (попытки сломать систему нестандартными сценариями). Нужно убедиться, что багов нет и что **все правила enforced на сервере**, а не только в UI.

## Как проводить аудит (метод)

1. **Сначала пойми модель** — прочитай `docs/REQUESTS-MODULE.md`, `docs/PERIOD-LOCK-2026-08-29.md`, `docs/DAY-STATUS-MODEL.md`, и ключевой код: `apps/api/src/routes/tasks.ts`, `apps/api/src/routes/day-entries.ts`, `apps/api/src/services/periodLock.ts`, `apps/web/src/components/DayFillCard.tsx`, `apps/web/src/components/MonthStrip.tsx`, `apps/web/src/pages/DashboardPage.tsx`, `apps/web/src/lib/taskWindow.ts`.
2. **Проверяй на ДВУХ уровнях:** (а) UI (кнопки прячутся/гаснут, тосты); (б) **сервер напрямую** — дёргай `PATCH/POST/PUT` в обход UI (curl/REST-клиент) и убеждайся, что сервер РЕЖЕТ (400/403), а не полагается на скрытую кнопку. Правило проекта: [[server-side-enforcement-never-trust-client]].
3. Для каждого пункта: ожидаемое поведение → фактическое → вердикт (✅/🐞) → если баг, минимальный воспроизводимый сценарий.
4. Тестовые данные — сид `packages/db/prisma/seed-august-demo.ts` (текущая неделя = незакрытые дырки). Пользователи `user@nexus.local` (обычный), `admin@nexus.local`.

## Модель (краткая опора — проверь, что реальность ей соответствует)

- **Состояния дня:** пустой → активный (есть начало, нет конца; **ровно один активный день на всех**) → закрытый (начало+конец+все задачи done). Выходной/отпуск/больничный/отгул — не «закрывают».
- **Жизненный цикл задачи:** назначили → **backlog**; **inprogress** только когда сам взял; **done** когда выполнил.
- **Взять/выполнить/создать свою «в работе»** — только когда АКТИВЕН день задачи (сегодня или прошлый дозаполняемый). Планирование в backlog и назначение другому — свободно.
- **Окно задачи = один день (startDate).** Дедлайн — «до какого числа успеть» (метка + флаг «просрочено» = `deadline < today && status≠done`), НЕ диапазон показа.
- **Дневная цепочка:** нельзя начать день, пока есть более ранний незакрытый рабочий день (сервер → 400). Выходные цепочка пропускает.
- **Период-lock:** старые недели (2+ недели назад / прошлый месяц) — read-only; override только мастер-админ.
- **Кнопка «Начать/Завершить» — переходящая** (штамп «сейчас»), только на рабочем дне сегодня/прошлом незакрытом; в выходной и в будущем — нет.
- **Приглушение в MonthStrip — по порогу** (самое раннее незакрытое число): до него серо, с него ярко.

## A. Свои задачи — жизненный цикл (один пользователь)

1. Назначенная мне задача падает в **backlog**, а не сразу в «на сегодня» (inprogress). Проверить и в UI, и в ответе API.
2. Взять задачу (backlog→inprogress) можно **только при активном дне** её `startDate`. При неактивном дне — кнопка/чекбокс не срабатывает + понятный тост; сервер режет прямой PATCH.
3. Отметить выполненной (inprogress→done) — только при активном дне. Снять галочку (done→inprogress) — задача **остаётся на своём дне**, НЕ прыгает на сегодня.
4. Создать свою задачу «в работе» на сегодня — можно только если сегодня активный день (иначе кнопка «Добавить задачу» = 🔒 с тостом-причиной).
5. Создать/спланировать задачу в backlog на будущее — свободно (без активного дня).
6. Редактирование названия/полей задачи (в т.ч. просроченной, где `startDate > deadline`) — не должно падать с ложной ошибкой «дата начала позже дедлайна».
7. Перенос задачи на другой день (drag на MonthStrip / смена startDate): окно = один день, задача уезжает целиком; после дедлайна → «просрочено».
8. Порядок задач дня (drag-reorder) — сохраняется, оптимистично, переживает F5.

## B. День и его связь с задачами

9. Нельзя **закрыть день** (проставить конец), пока есть незакрытые (inprogress) задачи ЭТОГО дня — тост «заверните или перенесите»; сервер режет.
10. Нельзя начать несколько дней (инвариант «один активный день»): начал день → не даёт начать другой, пока не закрыл.
11. Дневная цепочка: начал вторник — не даёт начать среду, пока вторник не закрыт (400 «Сначала закройте пропущенный рабочий день DD.MM»). Проверить и прямым PUT.
12. Кнопка «Начать/Завершить» ставит **текущее время всегда** (и для прошлого дня), дальше правится вручную.
13. Ретроактивное дозаполнение прошлого незакрытого дня (Начать → задачи → Завершить) — работает, порядок держит цепочка.
14. Выходной сегодня: зелёной «Начать» нет; запись работы = выбор места ИЛИ ручной ввод времени начала → день становится рабочим и стартует.
15. Будущий день: «Начать» нет, все контролы дня неактивны, время не логируется.

## C. Другие пользователи (кросс-юзер)

16. Отправка задачи другому пользователю: у него падает в **backlog**, ему приходит **уведомление** (регламент: любое действие над чужой сущностью → уведомление адресату).
17. Я НЕ могу взять/закрыть/удалить **чужую** задачу (где assignee ≠ я), даже прямым API. Проверить 403.
18. Автор задачи vs исполнитель: кто может менять дедлайн/название/перенос — проверить, что не-исполнитель и не-автор не может; сервер enforce.
19. Действия над моей задачей другим пользователем (переназначил, изменил дедлайн, закрыл) → мне уведомление; я вижу изменение (инвалидация, не только по F5).
20. Импersonation/охват: обычный пользователь не видит и не трогает задачи вне своего охвата; админ — по правилам.

## D. Корректность отображения (консистентность одной сущности)

21. «Задачи на сегодня» = задачи выбранного дня со статусом inprogress/done (окно = день). Совпадает со Сводом/канбаном по `startDate`.
22. Счётчики/чипы (выполнено/поставлено на день в MonthStrip) — совпадают с фактическим списком; обновляются мгновенно при действии (не только F5).
23. Флаг «просрочено» — единый критерий во всех местах (Обзор, «Дедлайны», канбан): `deadline < today && status≠done`.
24. Приглушение MonthStrip по порогу: до самого раннего незакрытого числа — серо, с него — ярко (включая выходные внутри диапазона). Сегодня/выбранный — не тускнеют.
25. Выходной отображается как обычный день (число обычной яркости + квадратик + «выходной»), не приглушён по «типу».
26. Закрытый рабочий день — иконка ✓; день с незакрытыми задачами/незакрытый рабочий — оранжевая точка.
27. Восстановление вида при F5: выбранный день/вкладка/месяц не сбрасываются.

## E. Период-lock / цепочка / порог (граничные)

28. Залоченная старая неделя — задачи/день read-only; кнопки гаснут (🔒), сервер режет запись (400 lock).
29. Мастер-админ может override lock; обычный — нет (403). Проверить прямым API.
30. Порог приглушения = самое раннее незакрытое число; если всё закрыто — порог = сегодня (прошлое серо, сегодня+будущее ярко). Проверить оба случая на сидах.

## F. Защита от дурака / попытки сломать (adversarial — ключевое)

31. Выбрали выходной, «начали» его позже задним числом, попытались добавить задачи — что происходит? Не должно создавать неконсистентное состояние.
32. Закрыли день → пытаемся вынести/перенести из него задачу в **предыдущий незакрытый** день — должно ли запрещаться? Проверить, что не ломает цепочку/лок.
33. Прямой `POST /tasks` с `status: 'inprogress'` и `startDate` в закрытом/будущем/залоченном дне — сервер обязан резать.
34. Прямой `PATCH /tasks/:id` — сменить `status` на done в неактивном дне; сменить `assigneeId` на чужого; выставить `startDate` в залоченный период — всё должно резаться.
35. `PUT /day-entries` — начать второй активный день; начать день при незакрытом раннем; проставить конец с висящими задачами; править залоченный день — всё 400/403.
36. Гонки: два быстрых клика «Взять»/«Начать»/«Завершить» подряд — нет двойного состояния (идемпотентность/инвалидация).
37. Часовые пояса / полночь: задача/день у границы суток (ночная смена — конец < начала) считается корректно; `startDate` не «уезжает» на ±1 день.
38. Пустые/битые данные: день без entry, задача без дедлайна, задача с `startDate` в прошлом и без исполнителя — не роняют UI (нет «X.find is not a function» и т.п.).
39. Удаление/архивирование задачи, у которой есть история/логи — не оставляет «сирот» (ср. постмортем vacation-orphan-day).
40. Клиентский guard vs сервер: для каждого «спрятанного» действия убедиться, что дёрнув API напрямую, его **не выполнить**.

## G. Что явно ВНЕ рамок этого аудита (не путать)

- Отображение отпуск/отгул в календаре (pending пунктиром / approved подпись) и задачи на днях отсутствия — **отдельный следующий шаг** (см. `docs/REQUESTS-MODULE.md` → «СЛЕДУЮЩИЙ ШАГ»), сейчас не реализовано, баги по нему не заводить.
- Больничный как заявка — не делаем.
