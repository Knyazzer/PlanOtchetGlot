Исследование: как корректно и не-геймируемо считать загрузку и эффективность сотрудника
Краткий вывод. Нельзя получить одну математическую метрику, которая одновременно объективно измеряет труд, ценность, загрузку и при этом не геймится. Эти величины нужно разделить: загрузка — планирование capacity, utilization — использование времени, delivery/flow — скорость и предсказуемость потока, quality — качество, outcome — ценность результата.
1. Что именно нужно измерять
Вопрос	Метрики	Уровень
Сколько работы назначено?	Load / Planned Load	Сотрудник / планирование
Насколько используется capacity?	Utilization	Сотрудник / команда
Как движется работа?	WIP, Throughput, Cycle Time, Age	Команда / поток
Насколько предсказуемо исполнение?	Estimate Calibration, Forecast Error	Команда / тип работы
Какое качество?	Rework, Defects, Escaped Defects	Команда / продукт
Получен ли полезный результат?	Outcome / Business Metric	Продукт / бизнес
2. Почему модель 1/k не является эффективностью
Распределение каждого момента времени между k одновременно активными задачами с коэффициентом 1/k полезно как механизм защиты от двойного учета времени: сумма времени по задачам не превышает фактически доступное время. Однако формула эффективности вида ΣEstimateCompleted / WorkedTime при этом фактически превращается в среднюю одновременность задач k. Она начинает вознаграждать многозадачность, хотя context switching и параллельная работа могут снижать качество и скорость.
Следствие: concurrency лучше измерять отдельно как WIP и context switching, а не превращать его в положительный множитель производительности.
3. Рекомендуемая модель загрузки
Available Capacity:
C = Working Hours − Leave − Holidays − Other Non-available Time
Committed Load:
Load = Σ Initial/Committed Estimate / Available Capacity
Например, при capacity 8,5 ч и committed work 10 ч загрузка составляет 117,6%. Это сигнал перегруза планирования, а не доказательство низкой или высокой эффективности сотрудника.
4. Assigned Load и Committed Load нужно разделить
Assigned — все задачи, назначенные сотруднику. Committed — работа, которую реально планируется выполнить в конкретном периоде. Backlog может давать Assigned Load 200%+, одновременно с нормальным Committed Load около 80–100%.
5. Time tracking: не пытаться измерить «истинные часы задачи»
Для knowledge work фактическое время конкретной задачи часто не является непосредственно наблюдаемой физической величиной: часть работы происходит в размышлениях, обсуждениях, ожидании, параллельной деятельности и переключениях. Поэтому интервалы лучше использовать для распределения capacity, а не как доказательство точного количества часов, потраченных именно на задачу.
Практический вариант: один focused work item = 100% allocation; при реальной параллельной работе пользователь явно задаёт доли, например 70/30. Автоматическое 1/k лучше не использовать как утверждение фактического внимания.
6. Оценки: Estimate Accuracy и Calibration
Initial Estimate должен фиксироваться до начала работы.
После начала изменение оценки хранится отдельно: Initial Estimate → Revised Estimate.
Estimate/Actual можно использовать для обучения и калибровки планирования, но не как рейтинг сотрудника.
Calibration Ratio = ΣActual / ΣInitialEstimate
Лучше анализировать распределение и квантили, например P50/P75/P90, по команде, типу работы и классу сложности.
7. Earned Value Management (EVM)
EVM разделяет Planned Value (PV), Earned Value (EV) и Actual Cost (AC).
SPI = EV / PV
CPI = EV / AC
EVM хорошо подходит проектам с baseline, определённым scope и понятным измерением завершённого объёма. Для индивидуальной оценки knowledge worker применять EVM напрямую не рекомендуется; лучше использовать его на уровне проекта/эпика, если EV действительно объективно определяется.
8. Agile / Story Points / Velocity
Story Points — относительная оценка размера/сложности, а не часы. Velocity полезна для прогнозирования команды по историческим данным, но не должна использоваться как KPI отдельного сотрудника. Сравнивать velocity разных команд или превращать points per employee в рейтинг — анти-паттерн.
9. Kanban и Little’s Law
Базовые flow metrics: WIP, Throughput, Cycle Time и Work Item Age.
Little’s Law: WIP = Throughput × Average Cycle Time
Это позволяет анализировать поток без попытки доказать индивидуальную продуктивность. Например, при WIP=10 и throughput=20 задач/неделю средний cycle time около 0,5 недели.
10. Flow Efficiency
Flow Efficiency = Value-Adding Time / Elapsed Time
Метрика полезна для поиска ожиданий, блокировок и узких мест, но плохо подходит для оценки сотрудника: не всегда однозначно определить, что считать value-adding time.
11. Context Switching и параллельная работа
Concurrency не следует награждать. Лучше измерять его отдельно:
Average WIP = среднее число одновременно активных work items
P95 WIP = 95-й перцентиль одновременного WIP
Switch Rate = Context Switches / Focused Work Hours
Average Focus Block = Focused Work Time / Number of Focus Blocks
Высокие значения — диагностический сигнал процесса, а не автоматический штраф сотруднику. Причиной могут быть support, incidents, meetings, priority changes и зависимости.
12. Utilization в PSA и консалтинге
В Professional Services Automation часто используется Billable Utilization:
Utilization = Billable Hours / Available Hours
Это бизнес-метрика capacity/revenue: она отвечает, какая доля доступного времени ушла на оплачиваемую клиентскую работу. Она не является универсальной метрикой продуктивности разработчика или knowledge worker.
13. Ценность нельзя надёжно вывести из количества часов
Hours ≠ Value. Не стоит создавать субъективный Value Score для каждой задачи и затем оптимизировать Value/Hour. Это просто создаёт новый объект для гейминга.
Лучше связывать Task → Deliverable → Outcome → Business Metric. Например: реализована оптимизация → P95 latency снизилась → конверсия улучшилась. Чем дальше вправо по цепочке, тем менее корректно приписывать результат одному сотруднику.
14. Анти-гейминг: обязательные правила
•	Дробление задачи не должно автоматически увеличивать score; для технического дробления агрегировать показатели по parent item.
•	Initial Estimate фиксируется до начала работы и не переписывается задним числом.
•	Все изменения оценки сохраняются исторически.
•	Task completion должен иметь объективный Definition of Done.
•	Не использовать Tasks/Hour, Hours Completed/Hour, Story Points per Employee, WIP Bonus, Lines of Code или Commits/Day как KPI.
•	Не использовать Estimate/Actual как прямой индивидуальный рейтинг.
•	Сравнивать человека прежде всего с собственным baseline, а команды — с сопоставимыми командами.
•	Использовать distributions и percentiles, а не только средние.
•	Метрики должны иметь взаимные противовесы: throughput ↔ quality, utilization ↔ WIP/cycle time, estimate accuracy ↔ scope changes.
15. Минимальный честный набор метрик для внутреннего таск-трекера
Метрика	Формула / определение	Что отвечает	Уровень
Load	Committed Estimate / Available Capacity	Не перегрузили ли планированием?	Сотрудник / план
Utilization	Allocated Productive Time / Available Capacity	Куда ушло capacity?	Сотрудник / команда
WIP	Active Work Items	Сколько работы одновременно тащится?	Команда / поток
Throughput	Completed Items / Time	С какой скоростью доставляем?	Команда
Cycle Time	Finished − Started	Сколько длится доставка?	Команда / тип работы
Estimate Calibration	ΣActual / ΣInitialEstimate	Насколько хорошо планируем?	Команда / тип работы
Quality	Rework / Defects / Escapes	Не покупаем ли скорость качеством?	Команда / продукт
Outcome	Фактическая бизнес-метрика	Получен ли полезный результат?	Продукт / бизнес
16. Рекомендуемая архитектура показателей
CAPACITY → LOAD → FLOW (WIP / Throughput / Cycle Time) → QUALITY → OUTCOME
Time tracking должен прежде всего служить для capacity planning, cost accounting и диагностики процесса, а не для доказательства того, что сотрудник «работал ровно N часов».
17. Что делать с исходными кейсами A/B/C
В исходной модели A=100%, B=200%, C=300%, потому что формула фактически измеряет среднюю concurrency. В новой модели B и C не получают бонус за параллельность. Их concurrency/WIP фиксируется как характеристика процесса, а высокая сумма оценок относительно capacity отражается как planning load. Если оценки систематически сильно превышают распределённое время при параллельной работе, это сигнал калибровки estimates, а не доказательство того, что сотрудник в 2–3 раза эффективнее.
18. Итоговая рекомендация
Не строить один Employee Efficiency Score. Рекомендуемая граница ответственности: Load — персональный/плановый; Utilization — операционный; Flow и Quality — преимущественно командные; Outcome — продуктовый/бизнесовый. Concurrency и context switching — диагностические показатели. Такой дизайн лучше соответствует established practice и существенно снижает стимулы к дроблению задач, раздуванию оценок и запуску нескольких таймеров ради искусственной «эффективности».
Ключевые источники и стандарты для дальнейшего чтения
•	PMI — Earned Value Management / PV, EV, AC, SPI, CPI.
•	Kanban Guide — WIP, Throughput, Cycle Time, Work Item Age, Service Level Expectation.
•	Martin Fowler — Story Points и Velocity как инструменты прогнозирования, а не индивидуальной производительности.
•	DORA — software delivery metrics и предупреждение против превращения метрик в цели.
•	SPACE Framework — многомерное измерение developer productivity.
•	PSA practice — Billable Utilization как capacity/revenue metric.
